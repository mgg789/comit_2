# Вход через Яндекс ID

Сервер использует authorization-code flow. Кнопка в dev всегда отключена. В production она становится доступна после отметки согласия и положительного ответа `/api/auth/<role>/providers`; при отсутствии конфигурации остаётся вход по почте.

## Настройка приложения в портале Яндекса

1. Войдите под постоянным аккаунтом владельца сервиса на [страницу создания приложения для авторизации](https://oauth.yandex.ru/client/new/id/). Выберите «Для авторизации пользователей», название `Comit`, логотип и рабочую контактную почту владельца.
2. На шаге платформ выберите «Веб-сервисы». В Redirect URI внесите **оба** точных адреса:
   - `https://comit.droidje.com/api/auth/candidate/yandex/callback`
   - `https://comit.droidje.com/api/auth/employer/yandex/callback`
3. В доступах выберите только «Адрес электронной почты» (`login:email`). Фото, телефон, имя и дата рождения для этого входа не нужны.
4. Сохраните приложение. На карточке приложения возьмите Client ID и Client secret. Секрет храните только в окружении сервера. Для внешних пользователей выполните верификацию сервиса в Яндекс OAuth; до этого Яндекс может показывать предупреждение.
5. Не используйте тип «Для доступа к API или отладки»: он не предназначен для пользовательского входа и не поддерживает нужные callback.

Поля и последовательность сверены с [документацией регистрации](https://yandex.ru/dev/id/doc/ru/register-auth). Токен передаётся в [запрос информации о пользователе](https://yandex.ru/dev/id/doc/ru/user-information) через заголовок `Authorization: OAuth`, без токена в URL.

## Окружение API

После применения миграции `022_yandex_oauth.sql` передайте в контейнер API:

```dotenv
NODE_ENV=production
YANDEX_OAUTH_ENABLED=true
YANDEX_OAUTH_CLIENT_ID=<Client ID из портала>
YANDEX_OAUTH_CLIENT_SECRET=<Client secret из портала>
YANDEX_OAUTH_SITE_ORIGIN=https://comit.droidje.com
AUTH_ALLOWED_ORIGINS=https://comit.droidje.com
AUTH_COOKIE_SECURE=true
```

`AUTH_SECRET` остаётся обязательным по существующему контракту. Значения Client ID/secret не попадают во frontend. В dev `YANDEX_OAUTH_ENABLED` не включает провайдера. Если opt-in, один из секретов или HTTPS origin отсутствует, discovery возвращает `yandex: false`; email-вход продолжает работать.

После настройки владельцем проверьте `GET https://comit.droidje.com/api/auth/candidate/providers` и employer-вариант: ожидается `{"yandex":true}`. Затем пройдите реальный вход в браузере отдельно для каждой роли. Нельзя зарегистрировать один email в двух ролях.

## Защита и совместимость

Начало входа — POST с текущим согласием `account-v1` и доверенным Origin. Случайное состояние живёт 10 минут, связывается с HttpOnly/Secure/SameSite=Lax cookie браузера и ролью. Callback потребляет состояние в PostgreSQL до обращения к провайдеру; повторное получение кода и параллельные callback не создают повторную сессию. Запросы к провайдеру имеют таймаут, фиксированный HTTPS адрес и запрет перенаправлений; тело ошибки/токены не выводятся. Fastify request logging отключён для callback, чтобы code/state не попали в URL-логи приложения; при настройке внешнего reverse proxy также исключите query string callback из access log.

Аккаунт связывается с устойчивым Yandex `id`, а не автоматически с совпадающим email. Если email уже зарегистрирован в Comit, первый OAuth-вход получает `oauth_email_conflict`: используйте существующий вход по почте. Привязка провайдера к существующему аккаунту — отдельный будущий контракт; она здесь не имитируется. При последующем OAuth-входе смена email у провайдера не переносит связь на другой аккаунт. Ошибки показываются на форме входа; email-вход доступен при отказе пользователя или недоступности Яндекса.

Callback использует публичный `/api/` prefix nginx; backend маршруты начинаются с `/auth/`. URI регистрации должны совпадать с публичными адресами выше. Изменения SMTP и фактическая настройка портала/production не входят в локальную реализацию.

## Проверка регистрации 11.10.2026

Провайдер принял исправленную пару Client ID/secret: запрос с заведомо несуществующим кодом вернул `invalid_grant`, а не `invalid_client`; access token не выдавался. Публичные метаданные подтверждают `login:email` и основной callback кандидата. Поле `callback` содержит один основной адрес, поэтому не позволяет проверить весь список Redirect URI; наличие обоих адресов подтверждено владельцем приложения. Внутренние OAuth-тесты с одноразовым state и реальным PostgreSQL прошли (5/5). Реальный браузерный вход и production-конфигурация в эту проверку не входят; локальный dev по-прежнему не включает провайдера. Секреты в репозитории отсутствуют.
