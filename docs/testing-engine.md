# Testing engine — механика тестирования

> Статус на 11.10.2026: адаптивный браузерный контур работает для семи семейств,
> с реальной серверной проверкой MCQ и коротких ответов, записью по согласию,
> восстановлением попытки и публикацией предметного грейда. Реализованы отдельный
> изолированный судья Python и проверка развёрнутых ответов Jev/DeepSeek;
> выдача зависит от доступности соответствующего судьи.
> [Целевой дизайн](testing-design.md), [канон](../context/60-testing-engine.md).
> Entrypoint `python -m testing_engine` запускает `create_testing_app` и
> добавляет blueprint-маршруты `create_app`; UI публикуется по `/testing/`.
> Ниже описан текущий код; состояние конкретного стенда подтверждает smoke ([deploy.md](deploy.md)).

## Две анти-цели ТЗ и наш ответ

| Проблема ТЗ | Решение |
|---|---|
| Единый набор заданий → утечка | Параметризованные семейства, мораторий показанных экземпляров и ротация банка; расширение seed-банка для подтверждения устойчивости к утечке — следующий этап |
| Нейрогенерация под каждого → несопоставимая сложность | Уровень (L1–L4) задаётся банком; LLM генерирует варианты офлайн с валидацией. В сессии LLM проверяет только отдельный развёрнутый ответ по серверной рубрике |

## Entrypoint и blueprint-реестр

- `blueprints/*.yaml` — шаблоны (специализация, тема, тип, параметры, сложность); сейчас один файл `algo-hash-lookup.yaml`.
- `src/testing_engine/blueprints.py` — загрузка и валидация; каталог из `BLUEPRINT_DIR` (по умолчанию `./blueprints`).
- Маршруты: `GET /healthz`, `GET /ready`, `GET /blueprints`, `GET /blueprints/{id}` (404, если нет).
- Порт — `PORT` (по умолчанию 8102).

## Адаптивный контур (`create_testing_app`)

Хранилище — атомарные JSON-файлы в `TESTING_DATA_DIR` (по умолчанию `./data/testing`;
в compose — volume `testing-data`, `/data/testing`): `items.json` (банк) и
`sessions/<id>.json`. Файловое хранение — осознанный выбор для одного процесса; перенос в SQL — следующий этап при масштабировании.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/testing/preflight?specialization=...` | доступность, cooldown, текущая попытка, согласия и возможности судей без создания попытки |
| POST | `/testing/sessions` | `{specialization, declared_grade?, consents:{version, processing, video_analysis?, screen_recording}}` → `{session_id, status, tasks_given}`; владелец берётся из защищённого заголовка API |
| GET | `/testing/sessions/{id}/next` | следующее задание (без ответа); 409 `session_finished`/`session_complete`/`bank_exhausted`, 404 `session_not_found` |
| POST | `/testing/sessions/{id}/answer` | `{item_id, answer}` → `{correct, judge_status, answered, decided_grade, status}` |
| POST | `/testing/sessions/{id}/supervision` | только агрегаты прокторинга → бейдж присутствия; 400 на некорректные/завышенные счётчики |
| POST | `/testing/sessions/{id}/media` | контур полной записи: 409 `recording_disabled`, пока `TESTING_RECORDING_MODE` ≠ `full`; 403 без согласия на запись экрана |
| GET | `/testing/sessions/{id}/result` | статус, грейд, постериор по четырём грейдам, ответы, бейдж, согласия |
| POST | `/testing/sessions/{id}/finish` | финализация материалов и публикация завершённого результата |
| POST | `/testing/sessions/{id}/abandon` | прерывание попытки без публикации грейда |
| DELETE | `/internal/candidates/{candidate_id}` | service-to-service purge: tombstone владельца, удаление его JSON-сессий и captured media; повторный вызов идемпотентен |

- **Банк.** При старте засеивается `bank_seed.initial_items()`: 44 задания семи
  семейств (`algorithms`, `sql`, `rest_api`, `python`, `react`, `docker`,
  `teamwork`) — 29 MCQ, 4 code, 4 extended и 7 short_answer, уровни L1–L4.
  Неизвестное `specialization` отклоняется с 422.
- **Адаптивность** (`adaptive.py`): старт с L2, байесовский постериор над
  intern/junior/middle/senior, следующий уровень — граница максимальной
  неопределённости. Ранняя остановка: лидер ≥ 0.70 и второй грейд отстаёт более
  чем в 2 раза (`DECISION_PROBABILITY`, `FLIP_RATIO`); потолок — 30 заданий.
  Целевой дизайн предусматривает 0.8; в коде действует 0.70.
- **Проверка ответов** (`judge.py`): MCQ — точное серверное сравнение; code —
  только через внешний сервис code-judge (`CODE_JUDGE_URL`): кандидатский код
  исполняется в изоляции, а не в testing-engine (issue #18). Если сервис
  недоступен, возвращается повторяемый 503, оценка не меняется. Развёрнутые ответы
  проверяются Jev/DeepSeek по рубрике; short_answer — по допустимым значениям.
  `LocalPythonJudge` всегда отключён, включая `TESTING_LOCAL_JUDGE=1`;
  эталоны генератора также проходят через отдельный code-judge.
- **Ротация и генерация** (`store.py`, `generator.py`, `rotate.py`): сгенерированные
  экземпляры выводятся из оборота после 3 показов или по возрасту (1 день);
  seed-задания не выводятся; показанное сегодня выдаётся повторно только если
  других активных вариантов уровня нет (relaxed-fallback, наименьший exposure first).
  `PYTHONPATH=src python -m testing_engine.rotate [--dry-run] [--daily-limit 50] [--min-stock 5]`
  добирает банк через DeepSeek (`DEEPSEEK_API_KEY`) с дневным ledger-лимитом
  (`ledger.json`) и валидатором (4 уникальные опции MCQ, эталонное решение
  проходит тесты, ≥3 пунктов рубрики, без дублей). Без ключа команда выводит
  устаревшие экземпляры из оборота и сообщает дефицит банка.
- **Прокторинг** (`supervision.py`): бейдж из агрегатов (≥95 % в кадре —
  «хороший», 85–95 % — «нормальный», 70–85 % или мульти-лицо — «средний», ниже —
  «низкий», без камеры — «не определён»); без полной записи кадры не покидают устройство.
  Reference-клиент: `static/proctoring-client.js`. Носители режима `full`
  хранятся 90 дней (`maintenance()`/`cleanup_expired_media`).
- **Публикация результата** (`publisher.py`): после финализации завершённой
  авторизованной сессии отправляет `POST /internal/testing/session-result`
  (`X-Internal-Token` = `TESTING_ENGINE_TOKEN`, URL — `TESTING_API_URL`) с
  `candidate_id` (UUID из `candidate_key`), `session_id`, `specialization`,
  `decided_grade`, `supervision_badge`, `tasks_answered`. Если API не настроен или
  недоступен, результат сохраняется в testing-engine. Cooldown пересдачи (7 дней)
  и повышения (30 дней) проверяет API ([api.md](api.md)).

## Сервис code-judge

`services/code-judge` — отдельный FastAPI-сервис (`python -m code_judge`, порт
`CODE_JUDGE_PORT`, по умолчанию 8106; данные — `CODE_JUDGE_DATA_DIR`, по умолчанию
`./data/code-judge`). Публична только liveness `GET /healthz`; `GET /ready` и
`POST /submissions` требуют внутренний токен. Broker принимает код до 20 000
символов, owner, idempotency key и серверные тесты, возвращает сохранённый
терминальный вердикт. `/ready` выполняет реальную проверку изоляции; при ошибке
исполнения инфраструктуры возвращается 503. DMOJ-упаковщик остаётся отдельной
утилитой и не участвует в HTTP-пути оценки. Есть `infra/code-judge.Dockerfile`,
compose для выделенной judge VM и отдельный CI isolation job. Подробности
изоляции — ниже; deployment — [deploy.md](deploy.md#изолированная-проверка-кода).

## Правила грейд-теста (ТЗ)

- Грейд не понижается принудительно; не прошёл — тест на уровень ниже; прошёл уверенно — предложение повысить.
- Смена грейда ограничена по времени: повтор теста не раньше 7 дней, подтверждение повышения — не раньше 30 дней (проверяет API); история подтверждённых результатов видна кандидату (`GET /candidate/testing-history`).
- Подтверждение предметного грейда присваивается только тестом и сохраняется отдельно для семейства; общий заявленный грейд профиля не переписывается.

## Валидация тестирования (обязательна к сдаче)

1. Test-retest: повторное прохождение на новых вариантах → стабильный грейд.
2. Дискриминативность: синтетические слабые/сильные сессии → разделяет ли скор классы.
3. Экспертная разметка: решения с эталоном → совпадение с автоскором.
4. Утечка: «слитый» вариант не решает следующий вариант того же семейства.

Каждый пункт — с числами в документации сдачи (критерий №2 — 25% оценки).

## Браузерный контур и приватность (2026-10-11)

Браузер обращается только к `/api/candidate/testing/*`. API проверяет кандидатскую сессию и origin мутаций, передаёт сервисный токен и ID владельца в приватный testing-engine (`TESTING_ENGINE_URL`, по умолчанию `http://testing-engine:8102`; таймаут 65 с для `answer` и 25 с для остальных вызовов, тело запроса до 3,1 МБ — `apps/api/src/routes/candidate-testing.ts`). До нажатия «Начать» preflight не создаёт попытку. Доступны только реальные семейства банка: algorithms, sql, rest_api, python, react, docker, teamwork; общий тест направления из этих результатов не имитируется. Максимум 30 вопросов. Повторное чтение возвращает текущий неотвеченный вопрос; правильные ответы, скрытые тесты и рубрики браузеру не передаются.

Старт требует `testing-media-v1` и согласия на запись экрана. Реальная загрузка видео включается `TESTING_RECORDING_MODE=full`; preflight сообщает recording_enabled, при выключенной записи сохраняются только агрегаты. Камера добровольна; без отдельного согласия webcam-чанки запрещены. Согласие с серверным временем сохраняется в попытке и manifest записи. Чанки ограничены 3 млн символов base64, суммарно 512 MiB на попытку; одинаковые номера и байты допускают безопасный повтор. Записи удаляются по manifest через 90 дней: проверка при старте сервиса и каждый час. При удалении аккаунта API сначала вызывает внутренний purge для candidate ID: tombstone блокирует новые попытки, а сессии и media удаляются до hard delete аккаунта. Endpoint принимает только `TESTING_ENGINE_TOKEN`; его ошибка блокирует завершение удаления аккаунта.

После последнего ответа клиент завершает загрузки, отправляет итоговую supervision и вызывает `/finish`. Только затем публикуется подтверждённый результат с итоговым бейджем. Пока публикация не подтверждена, результат не обозначается как записанный в профиль. `/abandon` сохраняет прерывание без публикации грейда и вводит семидневную паузу для того же семейства. Подтверждённые семейства сохраняются отдельно (`grade:<family>`), не переписывая общий заявленный грейд кандидата. Пересдача — через 7 дней, повышение — через 30 дней; preflight также учитывает результаты API.

Короткие текстовые ответы (`short_answer`) проверяются детерминированно по серверному списку допустимых значений после нормализации пробелов и регистра. Код в авторизованной попытке `algorithms`/`python` идёт вторым вопросом: до старта проверяется реальная готовность `CODE_JUDGE_URL`. Недоступность блокирует старт, не расходуя попытку. Выданное задание сохраняется целиком на сервере и не меняется после перезагрузки.

Preflight сообщает `supported_question_types`, `judges` (`code_required`, `code_ready`, `text_configured`, `types`) и `unavailable_reason`. `text_configured` означает только наличие настройки провайдера, а не успешный сетевой вызов. В семействах с рубриками развёрнутый вопрос при настроенном провайдере ставится вторым (после кода — третьим, если такой вопрос есть в банке). Подтверждённый отказ от камеры виден работодателю в актуальном защищённом профиле; старое отсутствие metadata обозначается отдельно как unknown.

Ротация банка сначала отбирает допустимые типы и исключает вопросы текущей сессии, затем предпочитает ещё не показанные сегодня задания. Если они закончились, повтор между разными владельцами допускается среди того же допустимого набора. Новые MCQ после пополнения банка не скрывают обязательный второй `code` или `extended`; снятые с публикации задания не возвращаются при fallback.

### Изолированное выполнение кода

Testing-engine не запускает Python кандидата: прежний `LocalPythonJudge` всегда возвращает `local_judge_disabled`, включая тестовый флаг. Эталон генератора также проверяется отдельным broker. Внутренний `POST /submissions` принимает owner, idempotency key и серверный набор тестов; обязателен `CODE_JUDGE_TOKEN`. Браузер не управляет тестами или Docker-параметрами.

На каждый testcase создаётся отдельный контейнер: без сети и mounts, UID 65534, read-only rootfs, cap-drop ALL, no-new-privileges, 128 MiB RAM, 0.5 CPU, 16 процессов, CPU ulimit 3 секунды, ограниченный wall timeout и 64 KiB общего вывода. Логи Docker отключены. Broker сравнивает строгие JSON-значения с эталоном вне контейнера; эталон не передаётся в candidate process. CLI и контейнер принудительно удаляются по таймауту. `/ready` реально проверяет cgroup v2 CPU/memory/pids, UID, capabilities, no-new-privileges, network namespace и read-only FS; ошибка удаления контейнера означает недоступность.

`CODE_JUDGE_IMAGE` задаёт доверенный заранее загруженный образ; production deployment должен фиксировать digest. Docker API принадлежит отдельному sandbox daemon на выделенной границе исполнения; host Docker socket приложения подключать нельзя. Один процесс broker сериализует выполнение; один процесс testing-engine обслуживает file-backed sessions. Следующий шаг масштабирования на несколько воркеров — общая транзакционная БД и блокировки.

Запуск контейнера имеет отдельный таймаут 10 секунд: служебный маркер отправляется до выполнения кода кандидата, поэтому ошибка запуска означает 503, а не неправильный ответ. После маркера действует лимит 5 секунд, общий бюджет набора тестов — 25 секунд; исчерпание общего бюджета тоже возвращает недоступность. При штатном завершении контейнер удаляет единственный владелец — `finally` broker. При старте broker убирает только контейнеры с собственной меткой `comit.code-judge=managed` (до 16, без общего prune). После аварийного завершения broker оставшийся контейнер сохраняет все ресурсные ограничения до перезапуска или уборки оператором; выделенный daemon обслуживает ровно один экземпляр broker.

### Рубрики и повтор ответа

`JEV_API_KEY` включает Jev (`JEV_API_URL`, по умолчанию `https://ai.sverk.tech/v1/systemone`, модель `kev-latest`). Иначе используется `DEEPSEEK_API_KEY`, опционально `DEEPSEEK_BASE_URL` и `DEEPSEEK_MODEL`. При ошибке настроенного Jev нет скрытого переключения на другого провайдера. Рубрика находится в доверенной части запроса, ответ кандидата — отдельные недоверенные данные; провайдер возвращает только значения по каждому критерию. Jev вероятности проходят проверку диапазона/нормировки/уверенности ≥0.8; DeepSeek возвращает строгие JSON boolean. Все критерии должны быть выполнены. Итоговый грейд рассчитывает исключительно adaptive engine. Инструкции разделяют доверенные правила и ответ, что снижает влияние prompt injection; итоговый грейд в любом случае считает только adaptive engine.

Валидные рубричные ответы кэшируются по владельцу, провайдеру, модели, вопросу, рубрике и ответу. Broker хранит идемпотентный вердикт; повтор другого содержимого с тем же ключом запрещён. При сетевой ошибке, неправильной форме ответа или недоступном runner сервер возвращает 503, не меняет posterior/answered/exposure и сохраняет текущий вопрос. Уже отправленный текст фиксируется как pending: повторяют тот же ответ; после успешного вердикта повтор не вызывает оценку заново. Новые развёрнутые ответы требуют сети; полностью офлайн доступны MCQ/short_answer, локальный изолированный code runner и ранее закэшированные рубричные вердикты.

`GET /next` возвращает владельцу `pending_answer: string | null` для восстановления отправленного текста после перезагрузки. Это текст кандидата, а не эталон. Внешние запросы выполняются вне event loop; слабые ссылки на блокировки владельцев сериализуют изменения попытки без бессрочного накопления lock-объектов. `JEV_MODEL` позволяет явно выбрать модель вместо стандартной `kev-latest`.

Проверки: `PYTHONPATH=services/testing-engine/src:services/code-judge/src python -m pytest services/testing-engine/tests services/code-judge/tests`. Реальная Docker-приёмка выполняется отдельно: `CODE_JUDGE_DOCKER_TESTS=1 PYTHONPATH=services/code-judge/src python -m pytest services/code-judge/tests/test_docker_acceptance.py`. По умолчанию этот тест выключен и запускается явно; unit-тесты не выполняют candidate code на хосте.


### Граница доверия к наблюдению

Браузерные счётчики — вспомогательные сигналы. Сервер привязывает их к владельцу,
ограничивает длительность временем попытки, запрещает уменьшение checkpoint и
сохраняет отказ от камеры. Клиентский JavaScript находится у пользователя, поэтому
сервер не опирается на счётчики как на единственное доказательство. Работодатель
видит автоматическую отметку присутствия с пояснением; вывод о добросовестности
остаётся за человеком.
При разрешённой полной записи материалы предназначены для отдельной ручной
проверки, а не публичного доступа. Режим записи фиксируется при создании попытки:
последующее включение env не меняет согласия уже начавшего тест кандидата.


### Браузерная регрессия

`apps/testing/tests/browser-acceptance.mjs` проверяет квадратные чекбоксы
(1440/390 px), возобновление той же попытки с записью, сохранённые счётчики,
повтор после потери ответа и прерывание без грейда. Использует только
`startTestingBrowserFixture` (`apps/api/tests/helpers/testing-browser-fixture.ts`)
с аккаунтом `selftest@example.invalid` и виртуальные устройства Chrome.
Нужны запущенные fixture и UI, приватный storage state после dev-входа:

```sh
TESTING_FIXTURE_METADATA=/private/tmp/testing-fixture.json \
TESTING_STORAGE_STATE=/private/tmp/testing-state.json \
TESTING_UI_URL=http://127.0.0.1:5185 \
node apps/testing/tests/browser-acceptance.mjs
```

Playwright должен быть установлен отдельно; `PLAYWRIGHT_MODULE` позволяет
указать путь к его ESM-модулю. Метаданные содержат `apiUrl`, `engineUrl`,

### Полное отключение тестирования в локальном режиме

`TESTING_ENABLED=false` закрывает все `/testing/*`, кроме авторизованного
`GET /testing/preflight`: ответ `eligible=false`, `unavailable_reason=testing_disabled`.
Остальные операции возвращают `503 {"detail":"testing_disabled"}`, в том числе
доступ к уже начатой попытке. Существующие попытки и результаты сохраняются;
judge не вызывается, ответы не засчитываются, новые попытки не создаются.
Флаг по умолчанию `true` в engine; canonical local launcher задаёт `false`.
Все направления отключаются одновременно, включая MCQ. `/healthz` остаётся живым.
Testing UI не предлагает продолжить существующую попытку и не запрашивает камеру
или показ экрана в отключённом setup. Реальный режим включается через
`infra/local-dev.sh --with-judge` ([deploy.md](deploy.md)).

## Неоценённые ответы и публикация результата (#32, #37)

Открытый ответ фиксируется перед проверкой и повторно отправляется с тем же текстом. Количество неудачных проверок хранится в задании как `judge_attempts`: первые две возвращают 503, третья завершает сессию со статусом `abandoned`, `failure_reason=judge_unavailable`, `correct=null` и `judge_status=unjudged:<reason>`. Posterior, число оценённых ответов и подтверждённый грейд не меняются. Досрочное завершение, пока открытый ответ остаётся неоценённым после ошибки судьи, также получает эту причину. Сессия не публикует грейд и не создаёт семидневный кулдаун; предыдущие завершённые попытки продолжают определять законный срок пересдачи. `next_attempt_at=null` у такой сессии сообщает об отсутствии нового ограничения, а preflight остаётся источником итоговой доступности. UI освобождает показ экрана и полный экран, показывает причину и предлагает вернуться в резюме.

Jev с валидным распределением вероятностей, но уверенностью меньше 0.8, возвращает отдельное `rubric:uncertain`. Такая неопределённость кешируется по вопросу/ответу/владельцу/модели и не превращается в неправильный ответ. Некорректные вероятности или сетевой сбой остаются `text_judge_unavailable`.

Code-judge считает лимит времени кандидата отдельно: максимум 5 секунд на кейс и 25 секунд выполнения суммарно. Превышение даёт кешируемый `timeout`/`correct=false`. Старт и очистка контейнеров не включаются в этот бюджет; отдельный 45-секундный wall limit проверки относится к инфраструктуре. Выходы 125/126/127 после trusted readiness marker — `runtime_error`; до маркера — инфраструктурная ошибка. Выполнение остаётся только в изолированных Docker-контейнерах, локального fallback нет.

Broker сериализует только одинаковые `(owner,idempotency_key)`, сохраняя durable replay и conflict. Разные решения ограничиваются семафором `CODE_JUDGE_CONCURRENCY` (по умолчанию 2, допустимая величина 1–4). При занятых слотах после короткого ожидания возвращается 503 `runner_busy`; очередь не удерживает HTTP-клиента бесконечно. `/ready` выполняет независимый реальный probe без lock всех решений. File-backed broker по-прежнему предполагает один процесс на data directory.

Публикация результата выполняется вне event loop. `urllib.HTTPError` сохраняет `api_status:<HTTP code>`, безопасный `detail` и дату `retry_at`. Для `grade_upgrade_cooldown`/`retake_cooldown` API передаёт точную дату от последнего принятого результата; UI объясняет отказ и сохраняет прежний грейд. Постоянные HTTP 4xx терминальны (кроме 408/429). Сетевые ошибки, HTTP 5xx/408/429 имеют не более трёх попыток с минимальной паузой 5 и 10 секунд; после исчерпания UI не предлагает бесконечный повтор. Не принятый результат остаётся сохранённым для поддержки, алгоритм оценки и сроки 7/30 дней не меняются.

### Timeweb для генерации и rubric fallback

Генератор банка и fallback rubric judge используют `LLM_PROVIDER=timeweb`,
`TIMEWEB_API_KEY`, `TIMEWEB_BASE_URL=https://api.timeweb.ai/v1`,
`TIMEWEB_MODEL=timeweb/gpt-oss-120b` и `TIMEWEB_REASONING_EFFORT=low|medium|high`
(по умолчанию `low`). При настроенном `JEV_API_KEY` rubric сохраняет приоритет
Jev. Seed bank остаётся доступен при ошибке генерации. Ошибки провайдера
возвращают ограниченный код без тела upstream-ответа. DeepSeek остаётся
совместимым вариантом по умолчанию для локальных тестов.

Для rubric judge `JEV_PROVIDER=openrouter-mirror` задаёт протокол
`choice` через закреплённый
`JEV_API_URL=https://openrouter.droidje.com/api/alpha/decisions` с
`JEV_MODEL=typesafe/jev-1.13` и заголовком `X-Proxy-Token` (`JEV_API_KEY`).
Каждый rubric point получает критерии `not_met`/`met`; проверяются число
ответов, распределение вероятностей, совпадение choice и confidence ≥ 0.8.
Низкая уверенность возвращает неопределённость, а не ошибочную оценку кандидату.
