# Integration engine — внешние данные и верификация

> Статус: мок-реестр ФСП и демо-привязка работают; проверку фактов выполняет
> `services/verification-engine`, импорт и evidence пишет api-core. Скоринговый
> ФСП promotion-слой подключён после R₀; по умолчанию режим `shadow` не меняет выдачу.
> Решение о выделении сервиса — 2026-10-05 (context/80).

## Назначение

Единая точка работы с внешними источниками данных профиля:

- **исходящие коннекторы** — получение и верификация данных из внешних реестров;
- **входящие моки** — демонстрационные реестры там, где реального API на хакатоне нет (ФСП).

## ФСП: как реестр используется в продукте

Реальный API ФСП не предоставляется намеренно (ТЗ §2) — команда сама проектирует,
какие сведения о достижениях продукт получает и как их использует. На мок-реестре
работает следующий контур (подробно — [verification.md](verification.md)):

1. **Привязка ФСП ID.** `fsp_id`/`fsp_claim_id` — server-managed поля профиля:
   обычная mutation профиля их отклоняет (`server_managed_field`). ID появляется
   только через демо-привязку `POST /candidate/profile/fsp/demo/authorize` →
   `POST /candidate/profile/fsp/demo/callback` (fixture `fsp-001`/`fsp-002`):
   api-core обменивает одноразовый код на запись реестра через
   `POST /fsp/demo/token` integration-engine (`X-Internal-Token`).
2. **Evidence.** Сама привязка сохраняется как evidence `external:fsp:<id>` со
   статусом `partial` (демо-реестр, `ownership_proven=false`), провенанс
   `fsp_hackathon_registry:demo-2026-10`. Импортированные достижения реестра
   становятся achievement-claims со статусом `confirmed` внутри синтетического
   реестра; повторный импорт сохраняет их стабильные ID, смена ФСП-профиля
   требует отвязки. Повторная проверка уже привязанного `fsp_id`
   (`POST /candidate/profile/verifications/fsp`) идёт через verification-engine (`POST /verify/fsp`): найденный участник →
   `partial`, отсутствие в реестре → `rejected` (`fsp_not_found`, API отвечает
   422), `live_unbound` → `pending`. Подтверждение ставит только сервер.
3. **Карточка и PDF.** Matching projection переносит из FSP evidence только
   ранг, рейтинг и турниры (с пометкой демо-реестра) в карточку витрины; PDF
   печатает строку «Демо-реестр ФСП: рейтинг …, разряд …» в разделе «Внешние
   подтверждения». `display_name` из реестра в evidence и snapshot не попадает.
4. **Влияние на подбор.** Сейчас FSP evidence на основной скор не влияет:
   combine-скоринг не читает ни внешние подтверждения, ни achievement-claims.

Предлагаемая структура профиля участника (мок: `src/integration_engine/fsp_mock.py`):

```json
{
  "fsp_id": "fsp-001",
  "display_name": "Иван Иванов",
  "rank": "I",
  "rating": 1876,
  "events": [{"title": "...", "year": 2025, "place": 7}],
  "certificates": ["Школа ФСП: алгоритмы, 2024"]
}
```

`display_name` остаётся только в реестре: api-core сохраняет ранг, рейтинг,
достижения, турниры и сертификаты; в карточку витрины идут ранг, рейтинг и
турниры, в PDF — ранг и рейтинг.

## ФСП: подключённый promotion-слой

`fsp_boost.py` реализует `near-equivalent-promotion-v1`, подключённый после R₀.
Он не меняет combine-score, состав main top-k, веса или запечатанный R₀.
`MATCHING_PROMOTION_MODE=shadow` по умолчанию измеряет возможные перестановки;
`off` отключает слой, `active` применяет ограниченное продвижение почти равноценных кандидатов.

Формула: `0.02 × (0.5 × min(rating/2000,1) + 0.5 × rank_weight)`.
Веса разряда: MS=.12, КМС=.09, I=.06, II=.04, III=.03.
Отсутствующие или неподтверждённые факты дают ноль. Демо-факты разрешены только
при `APP_ENV=development` и `MATCHING_PROMOTION_ALLOW_DEMO=true`; они не становятся
реальным подтверждением ФСП. Источник — внешнее evidence профиля, а не
зарезервированное поле `CandidateProfile.fsp`.

Точные ограничения, UTC-недельная награда, identity и регрессии описаны в
[matching.md: дозированное продвижение](matching.md#дозированное-продвижение-fsp-и-еженедельной-активности).
Старое описание неподключённого draft-бонуса заменено этой реализацией.

## Обязательная семантика отсутствия истории

`GET /fsp/participants/{id}` → **404** — это нормальный, must-handle случай (ТЗ: «обязательна
только корректная обработка случая, когда истории ФСП у кандидата нет»). Платформа
рендерит профиль без блока ФСП, не ломая выдачу. Регресс-тест: `test_missing_fsp_history_is_404_not_500`.

## Демо-привязка ФСП

Мок также имитирует вход в ФСП для синтетических fixture-профилей (`fsp-001`, `fsp-002`):

- `GET /fsp/participants` — список fixture-записей для демо-выбора;
- `POST`/`GET /fsp/demo/authorize` — одноразовый код на 120 секунд; `redirect_uri` должен совпадать с `FSP_DEMO_CALLBACK_URL`;
- `POST /fsp/demo/token` — однократный обмен кода на запись реестра, только с `X-Internal-Token` = `FSP_DEMO_INTERNAL_TOKEN` (без настроенного токена — `503`);
- `GET /fsp/participants/{id}/achievements/{claim_id}` — отдельное достижение со стабильным `claim_id`.

Коды хранятся в памяти процесса. Проверку фактов профиля (ФСП, Git-репозиторий, hh.ru) выполняет
отдельный `services/verification-engine` — [verification.md](verification.md).
