# Email-уведомления

OTP уже отправлялся в HTML и plain text. Теперь оформление всех пяти типов
использует один шаблон: тёмный фон, капсула COMIT, встроенные CID PNG и footer
«Письмо отправлено сервисом Comit. Это не реклама». Табличная вёрстка и solid-color
fallback сохраняют читаемость без фоновых картинок, градиентов и внешних шрифтов.
HTML экранирует названия; в письмах нет контактов участников, текста чата или
закрытой ссылки на встречу.

| Тип | Источник и адресат | Макет Figma |
| --- | --- | --- |
| Код входа | Существующий auth challenge; заявленный email | `556:16766` |
| Ежемесячное задание | Кандидат; интеграционная функция для будущего сервиса заданий | `582:18599` |
| Собеседование работодателя | Новая запись `recruitment_interviews`; владелец процесса | `582:18493` |
| Собеседование кандидата | Та же запись; кандидат процесса | `582:18384` |
| Резюме понравилось | Подтверждённый `feed_pipeline.decisions.action='like'`; кандидат | `582:18271` |

Создание собеседования ещё может требовать подтверждения кандидатом. Письмо
сообщает о назначении, а не о согласии кандидата. Время показывается с датой,
годом и явно указанной зоной исходной встречи, чтобы не перепутать неделю или
местное время почтового клиента. Под временем размещена кнопка «Открыть
собеседование», ведущая в чат своего кабинета; ссылка также есть в plain text.

## Очередь и доставка

Миграция `013_notification_mail.sql` создаёт отдельный outbox. Триггер вставки
собеседования создаёт две записи в той же транзакции, что авторизованная команда.
Rollback отменяет письма; повтор CAS/idempotency-команды не создаёт новых писем.
Очередь не содержит email, имён или текста встречи: только UUID адресата/источника,
тип и срок. Единственное текстовое поле — название будущего задания.

Почтовый worker читает подтверждённые лайки из общей БД только после cutover-времени
миграции. Matching-таблицы остаются read-only; прежние лайки не запускают рассылку.
За проход импортируется до 100 новых фактов; уникальность `(account_id,kind,source_id)`
защищает от дублей после повторного запуска. Имя компании берётся из опубликованного
авторитетного draft, когда такое поле существует. Если компания там не названа,
письмо говорит «одной из компаний», без выдуманного имени или email работодателя.

Перед SMTP worker снова проверяет актуальный источник, адресат/роль, подтверждённый
email и согласие обработки аккаунта. Для всех событий нужен текущий processing
consent кандидата; лайки и ежемесячные задания также требуют pool consent.
Отменённая/прошедшая встреча, закрытый процесс, отозванное согласие или удалённый
источник переводят письмо в `dropped` с безопасным кодом `source_unavailable`.
Отзыв только публикации сохраняет возможность получить письмо по уже действующему
собеседованию.

Leases на 60 секунд, `FOR UPDATE SKIP LOCKED`, максимум пять попыток и backoff
30–240 секунд разделяют работу нескольких worker. Старый lease не может подтвердить
или перезаписать новое состояние. Доставка SMTP — **at least once**: crash после
SMTP ACK, но до DB ACK может повторить письмо; стабильный Message-ID помогает
почтовым клиентам распознать повтор, но не обещает exactly-once.

## Конфигурация и ограничения

После явной миграции используется существующая команда:

```bash
pnpm --filter @comit/api auth:mail-worker
```

`PUBLIC_SITE_URL` задаёт доверенный публичный origin для ссылок на кабинеты.
В production допускается HTTPS; в dev — также HTTP loopback. Credentials, path,
query и hash в этом значении запрещены. Значение берётся только из окружения,
не из заголовков запроса или данных участника. Без него worker сохраняет прежнюю
доставку OTP и не обрабатывает новую очередь событий. SMTP/TLS настройки остаются
существующими; ошибки источника уведомлений не останавливают доставку OTP.
Production rollout и изменение secrets/compose этой задачей не выполняются.

**Ежемесячные задания пока не имеют источника событий:** testing-engine предоставляет
только чтение blueprints; назначения кандидату, scheduler и рабочая страница задания
ещё не реализованы. Шаблон и `NotificationStore.enqueueMonthlyTask(client,
accountId, assignmentId, title, expiresAt)` проверены, но автоматическая рассылка
этого типа не включена. Будущий producer должен вызывать функцию в транзакции
реального назначения и обеспечить `/testing/#/tasks/<assignmentId>`; выдуманные
задания или cron-напоминания текущий код не создаёт.

## Проверки

```bash
pnpm --filter @comit/api exec tsx --test tests/auth-mail.test.ts tests/notification-mail.test.ts
NOTIFICATION_TEST_DATABASE_URL='postgres://…' pnpm --filter @comit/api exec tsx --test tests/notification-mail.pg.test.ts
```

PostgreSQL тест требует отдельной одноразовой БД. Проверены реальные транзакции
собеседований, rollback, две параллельные claims, cutover лайков, cancellation,
отзыв согласий, retry и fencing. SMTP заменён тестовым transport: фактическая
доставка в почтовые ящики и отображение в конкретных почтовых клиентах не проверены.
