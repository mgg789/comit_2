# Matching engine — механика подбора

> Статус: каркас. Полный дизайн — `context/50-matching-engine.md`; здесь — инварианты реализации.

## Пайплайн (комбайн вакансии)

```
Trigger (актуальная vacancy.ready со status=open | порог изменчивости пула)
  1. Strict pre-filter — специализация, грейд (допуски), формат; исключить visited/pending/attractive
  2. Hybrid scoring — score = w_r·rating + w_m·matchVec + w_f·fspBoost + w_a·freshness (w_r > w_m)
  3. top-k (k ≈ 20–50) → реранкер
  4. Selection + объяснение попадания (снапшот факторов)
  5. Сохранить Selection; бизнес-статус вакансии задаётся отдельно
```

## Инварианты (нарушать нельзя)

- Объяснимость обязательна (ТЗ: «краткая объяснимость выдачи», «обоснование попадания в подборку»): каждый Selection несёт структурированные факторы (топ совпавших фич, вклад рейтинга, ФСП-бейджи) — никогда не рукописные строки.
- Вектора гибридные: интерпретируемые фичи — основа скоринга и объяснений, плотный эмбеддинг описания — один из сигналов (решение Q5, context/80).
- **Уточнение цикла 1 от 05.10:** и подтверждённые, и неподтверждённые уровни
  входят в строгий вектор; статус и источник хранятся отдельно. Старое правило
  «только верифицированные» для intake заменено прямым решением Mike.
- Рейтинг (очки подтверждённого профиля) — отдельная ось от категории (категория присваивается только тестом).
- Тиндер-фидбек: лайк `v ← n(v + α·v_c)`, скип `v ← n(v − β·v_c)`, α > β; маскированные пробы — коррекция только маскированной подсекции.
- Переотбор: Visited — никогда; Pending — не трогаем; отклонённые возвращаются через порог изменения профиля.

## Валидация (обязательна к сдаче)

Синтетика: 200+ кандидатов, 10 вакансий с эталонной разметкой. Метрики: Precision@5/10 (прямо из критериев ТЗ), MRR, ablation (без вектора / без рейтинга / без ФСП-буста), сходимость тиндер-лупа на работодателе-агенте. Протокол и результаты — в документацию сдачи.

## Готовая воронка перед комбайном

Intake → eligibility → durable job → strict + Harrier + PDF → атомарный ready pool
+ outbox. Реализация в `services/matching-engine`, Fastify — защищённый транспорт.
Класс = primary_direction × принятый upstream grade. Внутри направления сортировка:
senior → middle → junior → intern, затем confirmed_strength по убыванию и UUID.
confirmed_strength = сумма confirmed уровней всех групп + число confirmed
проектов/мест опыта/достижений; это детерминированный tie-breaker, **не ratingPoints**.

Строгий вектор: каждое заявленное значение /7; partial/self_reported/pending
сохраняются наравне с confirmed как **уровни**, rejected/отсутствие → 0.
`strict_evidence[index]` различает эти состояния, сохраняя исходный уровень.
**Контракт комбайна:** числовой strict_vector нельзя использовать отдельно от
strict_evidence; коэффициенты доверия/веса относятся к следующему этапу и здесь
не выдумываются. Грейд и confirmed_strength учитывают подтверждение отдельно.

Мягкий вектор — самостоятельный 640D артефакт Harrier-270M. Текст содержит
описание, проекты, опыт, достижения и предпочтения с их статусами; rejected
claims остаются в private профиле, но не входят в текст. Неизвестные metadata
и контакты не подаются модели. Документы без query instruction — по
[карточке модели Microsoft](https://huggingface.co/microsoft/harrier-oss-v1-270m).
Закреплена ревизия `31de22b673913c7d658c0f03f792d77c2dcf8ebd`, CPU,
чанки по 1024 токена, среднее по длине чанков с финальной L2-нормировкой.
Runtime не скачивает модель: точный snapshot нужно подготовить заранее.
В пуле хранятся strict schema version/hash и semantic model version.

PDF генерируется из исходного профиля со статусами всех навыков; отдельные
public и owner проекции. Эмбеддинг не использует PDF, а комбайн не разбирает PDF.
Public скрывает известное имя, email/телефон и распознанные контакты/ссылки
в тексте. Автоматическая редакция не гарантирует удаление намеренно замаскированных
контактов/имён третьих лиц: upstream модерация текста остаётся обязательной.

Worker: 300-секундный lease с heartbeat, 5 попыток, backoff 30 секунд × 2^n
с капом 3600; параметры через PIPELINE_* env. Перезапуск подхватывает просроченные
jobs; исчерпанный лимит → failed с безопасным error_code, ручной retry после ремонта.
Outbox комбайна пока сохраняется в БД; доставка и event consumer — следующий этап.

## Готовая вакансия перед комбайном

Intake → checklist → durable job → strict/mask + optional Harrier → atomic ready/outbox.
Условия и маршруты — [API](api.md#подготовка-вакансии-к-комбайну-цикл-1).
Class-only, domain-only, stack-only и смешанные требования поддерживаются.
Класс не подставляет уровни навыков; отсутствие класса не выводится из текста.

Строгая координата = явно заданная относительная оценка /7. Requirement_mask=true
только для переданных ключей, включая уровень 0. Отсутствующий ключ имеет 0/false;
это отсутствие требования, а не требование нулевого навыка. Будущий комбайн
должен учитывать маску вакансии и evidence кандидата; для class-only строгий
вектор нулевой, поэтому cosine без доступных координат не применяется.
Оценки вакансии здесь не интерпретируются как жёсткие минимальные пороги.

Мягкий вектор строится только из непустого bio. Harrier получает vacancy query
с инструкцией искать подходящие профили; кандидаты остаются document inputs.
Обе стороны используют одну pinned модель, last-token pooling и L2, 640D,
одинаковый semantic_space_id; cache/model versions разных ролей различны.
Пустой bio даёт NULL и semantic_available=false. Заданный bio при недоступной
модели ждёт retry, сохраняя исходный текст. Подтверждение качества подбора
(Precision/MRR) относится к следующему этапу; этот acceptance проверяет подготовку.

## Основной отбор: правила первого рабочего прохода

Город обязателен у обеих сторон (решение Mike). Зарплатные интервалы должны
пересекаться включительно. Заданный class сравнивается с направлением кандидата;
отсутствующий class не создаёт ограничения направления. Формат должен быть явно
в work_types. Для onsite/hybrid нужен тот же город либо relocation_ready=true
с подходящим направлением переезда; remote не требует совпадения городов.
Применяется единая нормировка Unicode/case/пробелов/ё, префикса «г.» и небольшой
таблицы известных aliases. Неизвестные варианты/одноимённые города разных регионов
upstream должен задавать однозначным каноническим именем; геокодер не вызывается.

Main-v1 — ручная стартовая политика, не обученная модель. Рейтинг — percentile
существующего порядка grade/confirmed_strength внутри всего класса до фильтрации;
одинаковые grade/strength получают одинаковый score. Это не ratingPoints.
FSP и freshness сейчас не участвуют: структурированного источника этих сигналов нет.
Сохраняются базовые веса 0.45 для рейтинга и 0.35 для strict, нормированные по
доступным каналам вакансии. При class-only без навыков остаётся рейтинг.

Strict — среднее по явным координатам: agreement=1−abs(candidate_level/7−target/7),
умноженное на confidence статуса: confirmed=1, partial=0.8, self_reported=0.6,
pending=0.5, rejected/отсутствие=0. Неизвестное не совпадает с явным target=0.
Неподтверждённые значения продолжают участвовать; коэффициенты заданы открыто
в одной политике. Это относительное соответствие, не фильтр минимального уровня.

При совместимом semantic_space_id добавляется ограниченная поправка:
0.10×((1−base)×max(cos,0)+base×min(cos,0)). Score остаётся в [0,1], мягкий сигнал
не заменяет основной. Отсутствие bio/несовместимость пространства явны в explanation.
Top-k (default50, максимум500) получает детерминированный предварительный порядок;
реранкер и отбрасывание хвоста этим этапом не выполняются. Каждый результат
содержит структурированные вклады рейтинга/strict/semantic и top matched features.
