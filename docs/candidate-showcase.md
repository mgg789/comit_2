# Общая витрина соискателей

Backend работодателя позволяет искать актуальные публичные профили без
выбранной вакансии. UI в этот проход не входит. Витрина использует тот же
готовый пул, что комбайн, и не публикует черновики, отозванные согласия или
артефакты предыдущей ревизии/строгой схемы.

## Публичный API

Все пути ниже относительно `/api`; нужна действующая employer-сессия или
Bearer. `owner_id` выводится из сессии. Ответы имеют `Cache-Control: no-store`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/employer/candidates/search` | Поиск и следующая страница |
| GET | `/employer/candidates/:candidate_id` | Текущий публичный профиль |
| GET | `/employer/candidates/:candidate_id/resume.pdf?profile_revision=N` | Публичный PDF точной ревизии |
| POST | `/employer/vacancy-drafts/:draft_id/showcase-likes` | Лайк для собственной открытой вакансии |
| GET | `/employer/vacancy-drafts/:draft_id/showcase-likes/:idempotency_key` | Неизменяемая квитанция лайка |

Поиск принимает `q` до 500 символов, `limit` 1–100, непрозрачный `cursor` и
`filters`: `classes`, `grades`, `cities`, `salary` (`from_rub`/`to_rub`, RUB в
месяц), `work_types`, `relocation_ready`, `groups`. В groups независимые
`domains`/`stacks`/`soft_skills`; каждое условие задаёт `key`, `min_level` 0–7,
`statuses`. Требования групп соединяются AND; списки классов/городов/форматов
— OR. Зарплата проверяется на включительное пересечение. По умолчанию
сохраняются confirmed, partial, self_reported, pending; rejected допускается
только при явном выборе статуса. Неизвестные условия не становятся согласием.

Без `q` выдаётся весь подходящий пул по глобальному рангу внутри класса и
UUID. С `q` выполняются независимые PostgreSQL full-text и реальный локальный
Harrier `vacancy_query` в совместимом пространстве 640D. Ранги объединяются
RRF: сумма `1/(60+rank)` по имеющимся каналам. `search_factors` показывает
вклад каждого канала; поиск не подменяет скоринг конкретной вакансии.

`mode`: browse, hybrid или lexical. При отсутствии Harrier/совместимых
документных векторов lexical явно сообщает `fallback_reason`; фальшивые
векторы не создаются. Кэш хранит **только вектор запроса**, а не карточки или
результаты поиска: срок 24 часа, максимум 1000 записей, ключ включает
закреплённые модель/пространство и запрос. Каждая выдача заново проверяет пул.

Курсор связан с работодателем, запросом, фильтрами, каналами, схемой,
поколением пула и подходящими ID/ревизиями. Изменение этих данных возвращает
409; клиент начинает выдачу заново. Страницы читаются в repeatable-read.

## Профиль и контакты

`public_profile` версии 1 содержит анонимное имя `Candidate <UUID>`, город,
зарплату, условия работы, заявленные навыки и их статусы, очищенные тексты
проектов/опыта/достижений, разрешённые типизированные факты и предпочтения.
Email, телефон, настоящее имя, произвольные details/metadata, доказательства
и provenance не входят в DTO. Подтверждённые и неподтверждённые заявления
сохраняются с явными статусами.

Из публичного текста удаляются известные имя/контакты, email, телефонные
шаблоны, URL и handles. Такая очистка не распознаёт все обфусцированные
контакты или чужие имена; требуется модерация исходного текста. PDF использует
существующий публичный renderer с той же очисткой. Gateway читает только
фиксированный public-pool PDF, ограничивает размер 16 MiB и проверяет ревизию
и API source consent до и после загрузки. Частная owner-версия недоступна.

## Лайк и выбор вакансии

Клиент использует собственные `/employer/vacancy-drafts?limit=...&offset=...`
и `/:draft_id/ready`: подходят созданные/опубликованные черновики, для которых
ready возвращает текущую открытую вакансию. Без такой вакансии просмотр
остаётся доступен, лайк недоступен. Решение о допустимости принимает backend.

Лайк принимает `candidate_id`, точную `profile_revision` и UUID
`idempotency_key`. Собственник, ready/open, текущие согласия и ревизия/схема
обязательны. Несовпадение класса, зарплаты, города/переезда/формата возвращает
409 с `detail.code=strict_filter_confirmation_required`, массивом `warnings`,
ревизиями и `mismatch_token`. Кабинет работодателя показывает по нему окно подтверждения (`apps/employer/src/discovery.tsx`). До
подтверждения экспозиция, квитанция и saved не создаются. Работодатель может
повторить запрос с этим `mismatch_token` и тем же idempotency_key: карточка
сохраняется несмотря на несоответствие. Token связан с владельцем, вакансией,
обеими ревизиями, причинами и policy; изменившиеся условия требуют нового
предупреждения. Token не является секретом/токеном доступа.

Visited, pending, attractive, отсутствие согласия, устаревший профиль и чужая
или закрытая вакансия не допускают override. По одной вакансии нельзя
создать два saved для того же кандидата, в том числе конкурентными ключами.

В одной транзакции создаётся экспозиция `kind=showcase`, `mode=manual`, затем
применяется общий переход FeedStore: квитанция like, saved, attractive,
события allocated/delivered/like и новый запуск комбайна. Лайк доступен до
ML-запуска; main/rerank run не выдумывается. Точные повторы возвращают старую
квитанцию даже после отзыва профиля/закрытия вакансии; смена кандидата,
ревизии или mismatch_token под тем же ключом — 409. Предупреждения сохраняются
в receipt и saved.card.strict_filter_warnings, без ложной отметки о прохождении
строгого фильтра. Другой новый ключ уже сохранённого кандидата
— 409, новое членство/экспозиция не создаётся.

Saved, просмотр через экспозицию, приглашение, принятие, контакты, собеседования
и оффер используют существующий [recruitment](recruitment.md). Ручной источник
явно сохраняется в событиях; включение в ML-cohort экспорт и
обучение предпочтений — следующий этап; ручной источник не сбрасывает активную модель вакансии.

Сохранён общий pipeline advisory lock ради существующего порядка блокировок;
manual-транзакция ограничивает ожидание lock 5 s и отдельный statement 10 s.
При contention internal API возвращает 503/Retry-After; повторяется тот же
ключ. Переход от глобальной блокировки к более гранулярной — направление для масштабирования.

## Хранение и проверка

Миграция `011_candidate_showcase.sql` добавляет query cache/GIN, источник
feed-сессии и manual kind; прежние сессии получают source=tinder. Main/rerank
ID обязательны для Tinder и отсутствуют у showcase. Мигратор пересобирает
публичную проекцию существующего пула из его точной исходной ревизии, не меняя
векторы. Новые публикации используют тот же builder.

Проверки: `test_showcase_search*.py`, `test_showcase_likes_integration.py`,
`apps/api/tests/showcase.test.ts`. Для PostgreSQL-тестов задаются только
отдельные `PIPELINE_TEST_DATABASE_URL`/`SHOWCASE_ROUTE_TEST_DATABASE_URL`.
`tests/candidate_showcase_acceptance.py` проходит реальный HTTP-контур:
email auth через локальный encrypted mailbox, source profile, projection,
Harrier, поиск/PDF, публикация вакансии, manual like, saved, приглашение,
принятие/контакты, отзыв согласия и устаревший cursor. SMTP не вызывается.
Запуск требует собранного API на 39790 и отдельных matching/agents на 39791/39794,
пустой `comit_profile_acceptance_showcase` на loopback PostgreSQL25433 и
локального закреплённого Harrier; параметры задаются SHOWCASE_ACCEPTANCE_*.

Проведённые команды, результаты и пропуски:
[candidate-showcase-verification.md](candidate-showcase-verification.md).
