# Предпочтения конкретной вакансии

Следующий после R₀ этап из [раздела3 канона](../context/51-reranker-and-feed-learning.md)
реализован как обучение малой персональной поправки. Offline CLI сохраняет
**теневые** результаты; дополнительно подключён фоновый `preference-worker`,
который обучается на явных реакциях в контуре и применяет прошедшую проверку
версию к ещё не доставленным карточкам. Ограниченные research-показы гипотез добавляет отдельный слой ([hypothesis-learning.md](hypothesis-learning.md)), а не этот learner.
Детерминированные наблюдения проверяют механику; качество отбора из непоказанного пула оценивается отдельно.
R₀, Harrier, строгие фильтры и принадлежность к резерву остаются прежними.

## Что обучается

Для точной версии вакансии и базовой модели учатся15 коэффициентов: грейд,
рейтинг, совпадение домена/стека/soft skills, подтверждения домена и стека,
семантическое соответствие, релевантные проекты/опыт, эксплуатация, зарплатная
доступность и три взаимодействия. Сырые640 координат Harrier не переобучаются.

На train отдельно фиксируется логистическая калибровка `a + b·R₀/scale`, `b≥0`.
Затем регуляризованная логистическая модель учит остаток `δ·φ`. Сохраняются
ковариация аппроксимации Лапласа, доверие, точный порядок признаков, параметры
калибровки и совместимость с исходным артефактом. Внутренний logistic response
используется для диагностики; он не объявляется вероятностью найма или
калиброванной вероятностью лайка.

Признаки используют зафиксированные mean/scale R₀. Недоступное значение даёт
нулевую центрированную компоненту; коэффициенты отсутствия навыков не учатся.
Наблюдаемая компонента ограничивается±3. Персональная поправка:

`R = R₀ + scale·γ·clip(δ·φ, −0.5, +0.5)`.

`scale=max(1,‖w₀‖₂)` фиксируется для R₀, `γ≤0.5`. Это экспериментальные
версионированные ограничения, не измеренный оптимум для реальных работодателей.
Неопределённость, баланс меток и противоречия ограничивают доверие. Холодный
старт возвращает исходный score. Изменение имен/порядка/схемы признаков или
самого R₀ — ошибка совместимости, без скрытого дополнения нулями.

## Подготовка данных

Источник — [экспорт сборщика карточек](real-card-learning.md). Проверяются
manifest, SHA256 JSONL, hash каждого snapshot и совпадение baseline score
с исходными признаками. Незавершённые/обрезанные выгрузки и смешанные источники
отклоняются. Synthetic требует отдельного `--allow-synthetic`.

Контекст включает HMAC owner/vacancy, vacancy revision, strict/feature/main-policy
hashes, R₀ hash, activation revision и approval receipt. Старые или fallback
baseline exposures не смешиваются с совместимыми. Отсутствие реакции не получает
метку. Для like/dislike нужны событие явного действия и предшествующая доставка.
Подтверждение viewport само по себе не считается реакцией.

Кандидат внутри контекста даёт один первый пример, независимо от повторных
сессий и revisions профиля. При противоположных реакциях весь candidate group
в этом контексте исключается и отражается в quality counts. Согласующиеся повторы
не увеличивают число независимых примеров.

Первый проход сохраняет план разбиения **до fit**:60%train/20%validation/20%golden
по времени первой реакции. Одинаковое время не разрезается; один candidate group
не пересекает локальные части. Owner/vacancy намеренно общие для обучения
предпочтения именно этой вакансии; это не схема оценки новой глобальной R₀.
Изменённая выгрузка или план требует нового эксперимента. Для явного сброса
оператор указывает `--after` с timezone-aware cutoff в обоих проходах; старые
реакции не восстанавливают сброшенные предпочтения.

Минимум24train/8validation/8golden, в каждой части минимум две метки каждого
класса. Это порог проверки механики теневой модели, не допуск в живую выдачу.
При недостатке данных возвращается `needs_more_data`, fit не выполняется.
Гиперпараметры фиксированы, refit на golden не выполняется — golden остаётся честной отложенной выборкой. В отчёте отдельно logloss,
pair accuracy и NDCG@10 для validation/golden, paired bootstrap и model hashes.
Все результаты помечены `test_only`, `live_activation=false`, propensity неизвестна.
Logloss измеряет внутренний calibrated-offset response; pair/NDCG используют
отдельный ограниченный score в исходной шкале R₀. При slope, отличном от1,
это разные расстановки: улучшение logloss само по себе не доказывает улучшение
порядка. Ни одна из этих метрик не является пригодностью кандидата для найма.

## Команды

Из `services/matching-engine`, после создания полной приватной выгрузки:

```bash
PYTHONPATH=src .venv/bin/python -m matching_engine.preference_experiment plan \
  --export ../../data/learning/export-001 --output ../../data/learning/preference-plan-001
PYTHONPATH=src .venv/bin/python -m matching_engine.preference_experiment fit \
  --export ../../data/learning/export-001 \
  --plan ../../data/learning/preference-plan-001/plan.json \
  --key-file ../../data/learning/pseudonym.key \
  --output ../../data/learning/preference-fit-001
```

По умолчанию используется упакованный R₀; иной точный артефакт задаётся
`--baseline`. Operational fit требует `DATABASE_URL` авторитетной общей API/matching
БД и исходный приватный HMAC key(mode0600). Перед fit согласие всех участников
повторно проверяется; source row locks удерживаются до записи отчёта. Отзыв до
matching projection также блокирует fit. Нужно сделать свежий export и новый план.
После последующего отзыва готовые файлы/модели необходимо удалять и пересобирать.
Offline CLI не активирует модели и не отправляет данные наружу. Фоновый поток
описан ниже; он использует отдельный реестр в БД.
Результаты хранятся в новых каталогах0700/файлах0600, существующие не перезаписываются.

## Приёмка и границы

`tests/preference_learning_acceptance.py` выполняет настоящий fit и повторную
проверку воспроизводимости на480 **числовых симуляциях** шести разных предпочтений.
Это не новые candidate profiles, не независимая разметка людей и не реальный
датасет. Предыдущие60семейств, golden, ответы, usage и лимиты LLM не изменяются.
На маленьком экспорте прошлой приёмки с реальным Harrier есть только две реакции:
обучение требует больше данных. Production и реальные пользователи не запускались.

[Численный отчёт](../data/validation/vacancy-preference-acceptance.json): шесть
реально выполненных и сошедшихся fit,48/16/16 на контекст, повторные отчёты
побайтно одинаковы. Macro pair accuracy на golden симуляции0.585938→0.960938,
NDCG@10 0.654070→0.970931. Эти цифры характеризуют заранее заданные числовые
предпочтения, а не реальных работодателей. Проверены1115Python/PostgreSQL тестов,
включая26новых preference tests и два authoritative consent guard; API43passed,
один внешний QGramm test skipped. Typecheck/build/scoped Ruff и smoke12/12 зелёные.
Первый smoke не получил BLUEPRINT_DIR в отдельном testing child; после указания
штатного каталога blueprints повторный smoke прошёл, исходный лог сохранён.

## Фоновое обучение в контуре

Миграция `009_live_preferences.sql` создаёт отдельный durable реестр:
`controls`, `jobs`, `models`, `participants`, `events` в `preference_pipeline`.
Миграция `010_preference_event_clock.sql` фиксирует время события и постановки
задания после получения транзакционных блокировок; lease использует фактические
часы, а не время начала fit-транзакции. Исходные миграции сохранены.
`preference-worker` запускается вместе с остальными matching worker основного
compose (`infra/docker-compose.yml`) после `candidate-migrate`;
вручную: `python -m matching_engine preference-worker` с `DATABASE_URL`.
Ни обучение, ни применение поправки не требуют LLM, Harrier inference или
внешнего API. Worker использует уже зафиксированные признаки.

После первого набора **30 уникальных кандидатов** (понижено с 40 решением
оператора 08.10.2026 — [валидация](preference-convergence.md) показала сходимость
за ~20 реакций) транзакция like/dislike ставит одно задание в очередь. Повтор
события не добавляет работу или пример. Первый fit: 14 train, 8 validation,
8 свежего audit (`golden` в контракте существующего evaluator); минимум train —
`MIN_TRAIN_ROWS = 14`, версия live-политики — `vacancy-preference-live-v2`.
Версия и пороги входят в `policy_hash()`, а identity контекста сверяет
`preference_policy_hash`: контексты, зафиксированные под live-v1, после
обновления не считаются актуальными. Затем нужны **16 новых кандидатов**, не входивших
в предыдущую попытку: последние 8/8 снова проверочные, более ранние наблюдения
идут в train, ограниченный последними 1000 примерами. Старый audit может стать
будущим train, но не повторяется как проверка новой активации. Это последовательная
локальная проверка поведения, а не независимая golden для глобальной R₀.
Одинаковые timestamps на границе, недостаток обеих меток или конфликтующие
реакции блокируют fit/активацию. Неявные реакции не становятся отрицательными.

План с IDs внутренних записей, метками, временами и feature hashes сохраняется
**до fit** вместе с input/plan hashes. Признаки остаются в исходных samples;
в jobs не создаётся дополнительная копия профилей. Повтор после падения должен
восстановить те же sealed входы. Lease token, heartbeat и ограниченные retries
защищают от публикации старого worker и от дублирования модели. Новые реакции,
пришедшие во время fit, проверяются для следующего задания после публикации.

Версия становится активной только при сошедшейся модели с положительным trust,
наличии двух классов во всех частях, отсутствии ухудшения **raw ranking** pair
accuracy и NDCG на обеих проверочных частях и хотя бы одном строгом улучшении
порядка. Logloss не может ухудшиться более чем на 0.01. При замене сравнивается
также действующая модель на тех же свежих проверочных данных: ухудшение порядка
относительно неё запрещено. Это зафиксированный ограничитель эксплуатации,
не обученный оптимум или заявление о причинном выигрыше. При отказе сохраняется
последняя совместимая модель, при её отсутствии используется R₀.

Operational fit требует общей авторитетной API/matching БД. Source row locks
удерживают согласие участников до окончания fit и атомарной публикации;
matching consent повторно проверяется перед публикацией. Применение также
проверяет согласие **всех участников модели**, включая source-only отзыв до
matching projection. Отзыв стирает коэффициенты, plan/report payloads, оставляя
хеши и события; worker подбирает не доставленные matching отзывы после рестарта.

Контекст фиксирует vacancy revision, strict/feature/main policy, точный R₀,
его approval receipt и activation revision, source и live policy. Изменение
контекста делает старую модель неприменимой. Предпочтения не превращаются
в обязательные фильтры; кандидаты вне main top-k не оцениваются этим слоем.

## Доставка и управление

Доставленные карточки, их score/model/exposure identity и позиции не меняются.
На следующем запросе страницы новая модель переставляет только unserved suffix
после максимальной доставленной позиции, используя его существующие position
slots. Recommended/reserve сортируются отдельно. Транзакция перестановки
сохраняет все уже выданные position cursors; повтор страницы не создаёт другой
receipt. При равных personal scores используется main score, затем candidate ID.
Страница содержит `order_revision`, карточка — `preference_model_hash`,
`preference_revision`, `preference_position`, `preference_score`, поправку,
вклады признаков и `preference_state=baseline|personalized`.

Owner-scoped HTTP операции проксируются штатным employer/draft API:

- `GET /api/employer/vacancy-drafts/{draft_id}/preferences` — статус и счётчики.
- `POST .../preferences/retry` — повтор технически упавшего sealed задания.
- `POST .../preferences/rollback` — R₀ и выключение learning до явного reset.
- `POST .../preferences/reset` — R₀, новая epoch, обучение только на действиях
  после сброса и повторное включение worker для этой вакансии.

Тело POST: `idempotency_key` (UUID), `expected_revision` (CAS). Owner берётся
из проверенной employer session. Replay не повторяет действие, чужая вакансия
недоступна. Retry не обходит rejected gate и не переиспользует audit для новой
попытки настройки. Коэффициенты, участники и признаки через эти API не выдаются.
Журнал/экспорт сохраняет версии поправки и порядка, исходный R₀ score и
`propensity=null`: вероятность альтернативного показа не выдумывается.

Следующий отдельный этап — исследовательская политика с наблюдаемой поддержкой
альтернативных показов и проверка на настоящих реакциях. Delayed recruitment
outcomes и Harrier здесь не переобучаются. Обновление серверного контура и
production deployment в эту реализацию не входят.

## Приёмка фонового контура

[Отчёт](../data/validation/live-preference-acceptance.json) фиксирует отдельную
синтетическую PostgreSQL БД:48 профилей с реальным Harrier (640 координат),
40 явных реакций (прогон до понижения порога, live-v1), отдельный постоянно
работающий learner, автоматическую постановку задания, обучение24/8/8 и фактическую перестановку оставшегося хвоста.
На validation/audit синтетического примера pair accuracy улучшилась на0.625,
NDCG@10 — на0.32336. Это проверка механики, не измерение качества для работодателей.
Отзыв source consent вернул R₀ до matching projection и удалил коэффициенты;
reset исключил прежние реакции. Исходный private receipt сохраняется по хешу.

Воспроизведение: после сборки API задать `LIVE_PREFERENCE_ACCEPTANCE_DATABASE_URL`
для новой пустой loopback БД с префиксом `comit_live_preferences_` и выполнить
`PYTHONPATH=services/matching-engine/src services/matching-engine/.venv/bin/python tests/live_preference_acceptance.py`.
Нужны PostgreSQL/pgvector и установленный snapshot Harrier. Скрипт оставляет БД
и приватный отчёт в `tests/artifacts/live-preferences/`, останавливает свой worker.
Данные/признаки/модель не подменяются тестовыми реализациями; действия объявлены
синтетическими, внешние LLM не вызываются.

Полный Python/PG прогон:1128 passed без skips. После финальных изменений clocks
и метаданных доставки —28 affected tests passed; дополнительный тест ловит lease,
истёкший во время fit. API:44 passed,1 skip внешнего QGramm сервиса; typecheck,
build, scoped Ruff и `make smoke` (12/12) зелёные. Harrier E2E применил001–009;
010 затем применена в той же БД и проверена финальными PG тестами и smoke.

## Исследование предпочтений

Теперь [сопоставимые гипотезы](hypothesis-learning.md) добавляют ограниченные случайные pair/order назначения. Ранние deterministic receipts остаются историческими; новые research receipts имеют условные вероятности. Global propensity неизвестна, learner/gates продолжают оценивать наблюдаемую механику, не causal gain. Status selection_bias допускает legacy deterministic marker и текущий `feedback_unknown_global_propensity`.
