# Предпочтения конкретной вакансии

Следующий после R₀ этап из [раздела3 канона](../context/51-reranker-and-feed-learning.md)
реализован как отдельное обучение малой персональной поправки. Результаты сейчас
**теневые**: они позволяют оценивать порядок, но не переставляют действующие
карточки и не включают исследовательские показы. Детерминированные наблюдения
не доказывают качество отбора из непоказанного пула. R₀, Harrier, строгие фильтры,
резерв, стабильные позиции и курсоры действующей ленты остаются прежними.

## Что обучается

Для точной версии вакансии и базовой модели учатся15 коэффициентов: грейд,
рейтинг, совпадение домена/стека/soft skills, подтверждения домена и стека,
семантическое соответствие, релевантные проекты/опыт, эксплуатация, зарплатная
доступность и три взаимодействия. Сырые640 координат Harrier не переобучаются.

На train отдельно фиксируется логистическая калибровка `a + b·R₀/scale`, `b≥0`.
Затем регуляризованная логистическая модель учит остаток `δ·φ`. Сохраняются
ковариация аппроксимации Лапласа, доверие, точный порядок признаков, параметры
калибровки и совместимость с исходным артефактом. Внутренний logistic response
используется для диагностики; он не объявляется вероятностью найма или
калиброванной вероятностью лайка.

Признаки используют зафиксированные mean/scale R₀. Недоступное значение даёт
нулевую центрированную компоненту; коэффициенты отсутствия навыков не учатся.
Наблюдаемая компонента ограничивается±3. Персональная поправка:

`R = R₀ + scale·γ·clip(δ·φ, −0.5, +0.5)`.

`scale=max(1,‖w₀‖₂)` фиксируется для R₀, `γ≤0.5`. Это экспериментальные
версионированные ограничения, не измеренный оптимум для реальных работодателей.
Неопределённость, баланс меток и противоречия ограничивают доверие. Холодный
старт возвращает исходный score. Изменение имен/порядка/схемы признаков или
самого R₀ — ошибка совместимости, без скрытого дополнения нулями.

## Подготовка данных

Источник — [экспорт сборщика карточек](real-card-learning.md). Проверяются
manifest, SHA256 JSONL, hash каждого snapshot и совпадение baseline score
с исходными признаками. Незавершённые/обрезанные выгрузки и смешанные источники
отклоняются. Synthetic требует отдельного `--allow-synthetic`.

Контекст включает HMAC owner/vacancy, vacancy revision, strict/feature/main-policy
hashes, R₀ hash, activation revision и approval receipt. Старые или fallback
baseline exposures не смешиваются с совместимыми. Отсутствие реакции не получает
метку. Для like/dislike нужны событие явного действия и предшествующая доставка.
Подтверждение viewport само по себе не считается реакцией.

Кандидат внутри контекста даёт один первый пример, независимо от повторных
сессий и revisions профиля. При противоположных реакциях весь candidate group
в этом контексте исключается и отражается в quality counts. Согласующиеся повторы
не увеличивают число независимых примеров.

Первый проход сохраняет план разбиения **до fit**:60%train/20%validation/20%golden
по времени первой реакции. Одинаковое время не разрезается; один candidate group
не пересекает локальные части. Owner/vacancy намеренно общие для обучения
предпочтения именно этой вакансии; это не схема оценки новой глобальной R₀.
Изменённая выгрузка или план требует нового эксперимента. Для явного сброса
оператор указывает `--after` с timezone-aware cutoff в обоих проходах; старые
реакции не восстанавливают сброшенные предпочтения.

Минимум24train/8validation/8golden, в каждой части минимум две метки каждого
класса. Это порог проверки механики теневой модели, не допуск в живую выдачу.
При недостатке данных возвращается `needs_more_data`, fit не выполняется.
Подбор гиперпараметров и refit на golden отсутствуют. В отчёте отдельно logloss,
pair accuracy и NDCG@10 для validation/golden, paired bootstrap и model hashes.
Все результаты помечены `test_only`, `live_activation=false`, propensity неизвестна.
Logloss измеряет внутренний calibrated-offset response; pair/NDCG используют
отдельный ограниченный score в исходной шкале R₀. При slope, отличном от1,
это разные расстановки: улучшение logloss само по себе не доказывает улучшение
порядка. Ни одна из этих метрик не является пригодностью кандидата для найма.

## Команды

Из `services/matching-engine`, после создания полной приватной выгрузки:

```bash
PYTHONPATH=src .venv/bin/python -m matching_engine.preference_experiment plan \
  --export ../../data/learning/export-001 --output ../../data/learning/preference-plan-001
PYTHONPATH=src .venv/bin/python -m matching_engine.preference_experiment fit \
  --export ../../data/learning/export-001 \
  --plan ../../data/learning/preference-plan-001/plan.json \
  --key-file ../../data/learning/pseudonym.key \
  --output ../../data/learning/preference-fit-001
```

По умолчанию используется упакованный R₀; иной точный артефакт задаётся
`--baseline`. Operational fit требует `DATABASE_URL` авторитетной общей API/matching
БД и исходный приватный HMAC key(mode0600). Перед fit согласие всех участников
повторно проверяется; source row locks удерживаются до записи отчёта. Отзыв до
matching projection также блокирует fit. Нужно сделать свежий export и новый план.
После последующего отзыва готовые файлы/модели необходимо удалять и пересобирать.
Автоматической активации, расписания обучения и внешней отправки данных нет.
Результаты хранятся в новых каталогах0700/файлах0600, существующие не перезаписываются.

## Приёмка и границы

`tests/preference_learning_acceptance.py` выполняет настоящий fit и повторную
проверку воспроизводимости на480 **числовых симуляциях** шести разных предпочтений.
Это не новые candidate profiles, не независимая разметка людей и не реальный
датасет. Предыдущие60семейств, golden, ответы, usage и лимиты LLM не изменяются.
На маленьком экспорте прошлой приёмки с реальным Harrier есть только две реакции:
обучение требует больше данных. Production и реальные пользователи не запускались.

[Численный отчёт](../data/validation/vacancy-preference-acceptance.json): шесть
реально выполненных и сошедшихся fit,48/16/16 на контекст, повторные отчёты
побайтно одинаковы. Macro pair accuracy на golden симуляции0.585938→0.960938,
NDCG@10 0.654070→0.970931. Эти цифры характеризуют заранее заданные числовые
предпочтения, а не реальных работодателей. Проверены1115Python/PostgreSQL тестов,
включая26новых preference tests и два authoritative consent guard; API43passed,
один внешний QGramm test skipped. Typecheck/build/scoped Ruff и smoke12/12 зелёные.
Первый smoke не получил BLUEPRINT_DIR в отдельном testing child; после указания
штатного каталога blueprints повторный smoke прошёл, исходный лог сохранён.

Следующий отдельный этап для живой персонализации — корректный журнал версий
порядка, наблюдаемая поддержка альтернативных показов и проверка на настоящих
реакциях. Исследовательская политика и delayed recruitment outcomes здесь не учатся.
