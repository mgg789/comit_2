# Расширенная выборка R₀ с новой разметкой

Новая версия `rerank-grounded-cohort-v9` создаёт 60 семейств / 420 профилей
по восьми направлениям. Старые labels, источники и экспериментальные R₀
сохраняются. Это набор для глобального стартового реранкера: runtime-признаки
не кодируют индивидуальные приоритеты работодателя. Персонализация и активация
модели этим операторским проходом не выполняются.

## Источники и разбиение

Разбиение фиксируется до новых запросов: 32 train / 8 validation / 8 calibration /
12 golden, по исходному протоколу [файла 51](../context/51-reranker-and-feed-learning.md).
Каждая семья имеет семь кандидатов. В 12 старых семьях переиспользуются первые
шесть профилей и последний профиль с rejected-подтверждением, в исходных split
и ancestry. Gemma принял семь новых семейств, затем генерация остановилась:
null-статус заполненного факта и обрыв единственного исправления fullstack-01.
Версия v3 перенесла контракт этих семи источников, но два запроса Qwen на семь
профилей превысили текущий transport timeout 120 секунд. Ошибки и расход v3
сохранены; валидный teacher pilot v3 вновь совпал 20/20 и 10/10.
Версия v4 добавила ещё семь семейств, но несколько ответов застряли пробелами
после salary_min и исчерпали tokens. Версия v5 переносит все 14 новых источников
по цепочке точных source/job/raw hashes, сохраняя fold, требования и факты.
Для последующих семейств Gemma использовала prompt v4: компактный JSON, связанные
value/status объекты через anyOf, зарплата/длительность из enum и максимум два
уникальных project references на группу. V5 устранила salary stall, но два
ответа сохранили false/null-status и были отклонены. V6 требует либо пару
null/null, либо конкретное значение и один из пяти статусов. Availability
вычисляется по наличию фактов/ссылок, false и нулевая длительность считаются
предоставленными фактами. Это переименование полей, без извлечения из текста
и без исправления статусов. Исторические произвольные значения допустимых
диапазонов и более длинные списки остаются валидными. Один первый новый batch
проверяется до параллельного расширения. Общий транспорт ограничен
пятью одновременными запросами.

Новые профили используют навыки соответствующего направления из текущих 37
координат, плюс дополнительные координаты для покрытия схемы. Уровень и статус
каждого навыка раздельны; длительность, эксплуатация, роль и домены/стеки проекта
имеют свои статусы. Неизвестный факт остаётся null. Для mobile используется
доступная текущая таксономия гибридных интерфейсов; native Swift/Kotlin в реестре
нет, новая координата этим проходом не вводится.

Точные факты между независимыми семействами и одинаковые нормализованные
описания между splits запрещены. Для нового дублирующегося источника допустима
одна явная генерация-исправление; исходный receipt уходит в неизменяемую историю.
Исторические факты не переписываются. При исчерпанном исправлении источник
не становится учебными данными. Приблизительное сходство шаблонов не является
доказательством независимости; один generation batch остаётся одним семейством.

Признаки рассчитываются настоящими main scoring и feature builder, с общим
классным рангом по всем кандидатам направления. Новый Harrier640 semantic cache
начинается с копии старого и расширяется отдельно; query text соответствует
vacancy worker. Локальная тяжёлая инференция последовательна. Teachers получают
исходные синтетические факты и явные предпочтения, без main/model scores.
Полная lineage общего класса проверяется по точному составу профилей. Новые
эмбеддинги имеют отдельные неизменяемые receipts с model/text/vector hashes;
используемые seed-векторы сверяются с исходным кэшем, включая при возобновлении.

## Учитель и проверка

Один Qwen `qwen3.8-27b` через OpenAI-совместимый Sverk endpoint размечает пары
и независимо оценивает пригодность профилей. Новые kind-specific prompts имеют
отдельную cohort identity. Ответ содержит исходный статус каждого профиля
в отдельном поле, метку и точные типизированные ссылки,
без свободного объяснения, уверенности и вероятности найма. Все пять статусов,
включая rejected, сохраняются без превращения заявленного уровня в подтверждение.
Формальный грейд кандидата не заменяется оценкой пригодности 0–3.

Проверочный пилот содержит десять заранее зафиксированных случаев из всех
восьми направлений: 20 направленных пар и десять отдельных оценок пригодности.
Проверяются семь решающих случаев, ничья и два случая неизвестного обязательного
измерения. При exclusive criterion и отсутствующем измерении хотя бы одной
стороны допустим только insufficient; для отдельного профиля — null. Это
проверяемый кодом запрет подстановки других фактов, а не автоматическая правка
ответа. Пилот требует полного согласия с заранее записанными фактами/критериями.
Проверка ассистента не называется независимой человеческой оценкой.

Для семьи размечаются все 21 неупорядоченная пара и три выбранных обратных
ориентации. Reverse audits не добавляются в train как независимые примеры.
Каждому из семи профилей нужна новая отдельная оценка пригодности; прежние
grade labels не смешиваются. Менее двух из трёх совпавших swaps помещает семью
в карантин. Итоговый consistency gate требует минимум 162/180 swaps, отсутствие
карантинных семей и минимум шесть решающих пар в каждом golden family.
Циклы меток и их несовместимость со скалярным порядком публикуются без удаления.

## Бюджет и возобновление

До первого пилота ledger был generation 28 / pair 736 / grade 119. Первый
пилот v1 израсходовал 16 pair attempts и остановился на некорректном формате
строковых цитат и пропущенной ссылке на статус. Ни один ответ не принят.
Raw cache, failed jobs и `v1/failure-report.json` сохранены. Контракт v2 убирает
вложенное экранирование строк и проверяет статус отдельным обязательным полем.
Стартовый ledger v2: generation 28 / pair 752 / grade 119. После его пилота
и генерации: 41 / 771 / 129. Неуспешные попытки сохранены в v2, включая
`failure-report.json`; перенос уже принятых источников не расходует API.
Стартовый ledger v3: generation 41 / pair 771 / grade 129. После него 43/790/139.
Стартовый ledger v4: generation 43 / pair 790 / grade 139. Пределы остаются
120 / 3000 / 600, старые ошибки и повторы учитываются.
После v4 ledger 58/809/149; 26 семейств сохранены, включая 12 исторических.
Это старт v5; failed v4 responses и failure-report сохранены.
После v5 ledger 60/828/159; это старт v6. Pilot v6 повторно валидирован
из точных v5 request identities и raw hashes новым валидатором: 20/20 и
10/10, ноль HTTP и чтений ключа. Отсутствующий или изменившийся request cache
не заменяется сетевым вызовом. Hash v6 pilot:
`7d91bf797fa0687c85f1ae01ab515daaaf41307d002ffcc2cc77f2f75deaa0cc`.

После ожидаемых HTTP остаётся 732 pair и 21 grade attempts на исправления;
собственные job quotas консервативно также резервируют 30 cached jobs.
Текущий проход v9 переиспользует все 60 сохранённых семейств v7; новые
запросы генерации запрещены. V6 добавила 25 семейств, V7 — последние девять.
После генерации ledger: **99 / 828 / 159**, источники: **60 / 420**.
Консервативная граница профилей по hash-verified raw receipts равна 592.
Три явных производных описания в train учитываются дополнительно: **595 ≤ 600**.
При обрыве JSON учитываются завершённые внешние profile objects плюс один
начатый объект; неизвестный формат и отсутствие ответа стоят семь.
Частичный JSON служит только учёту расхода, его факты не принимаются.

V7 обнаружила три одинаковых описания между splits, без дубликатов типизированных
фактов. V8 сохранила явные train-перефразировки, но остановилась до HTTP/разметки
на несовместимости произвольных названий ролей с enum runtime-контракта.
V9 сохраняет исходный title и его статус в источнике/teacher. При runtime-проекции
точная enum-роль сохраняется; прочее название становится `other`, исходный title
сохраняется в private provenance. Категория роли по словам не выводится.

До новой разметки реальные Harrier-векторы и текущие признаки пересчитываются
для трёх перефразировок: data-03/0, data-03/2, fullstack-03/1. Сохранены исходные
и новые тексты, claim sets и hashes. Факты, уровни, зарплаты, статусы, split,
требования и предпочтения не меняются. Заранее фиксируются пределы: cosine
расстояние document-векторов ≤ 0.20, изменение semantic_cosine ≤ 0.25,
изменение main score ≤ 2 × semantic_correction; все прочие признаки и маски
должны совпасть. Проверка ассистента не считается человеческой.
Отчёт `description-repair-report.json` сохраняет три исходные коллизии и число
близких шаблонов (token Jaccard ≥ 0.6). Перефразировка устраняет точное совпадение
текста, но не доказывает независимость и не устраняет корреляцию шаблонов.

Сброса бюджета нет. Quota jobs консервативно включает обращения к кэшу;
фактический ledger учитывает HTTP, поэтому 20 пилотных jobs дали 19 HTTP
(одинаковая ничья в прямом и обратном порядке).
У любого запроса разрешён только attempt0 и один attempt1 с отдельным nonce.
Completed jobs воспроизводятся из точного raw cache без нового расхода.
Если после падения есть started receipt, но нет raw response, повтор автоматически
не отправляется: нужен разбор квитанции. HTTP auth/endpoint/schema failures явно
останавливают проход без серии одинаковых запросов.

Из корня репозитория:

```bash
PYTHONPATH=services/matching-engine/src services/matching-engine/.venv/bin/python -m matching_engine.rerank_cohort --pilot-only
PYTHONPATH=services/matching-engine/src services/matching-engine/.venv/bin/python -m matching_engine.rerank_cohort
```

Manifest, jobs, sources, features и dataset находятся в git-ignored
`tests/artifacts/reranker/rerank-grounded-cohort-v9/`. Manifest фиксирует код,
исходные receipts и quotas; изменение контекста требует новой версии.
Обучение и golden model predictions этой командой не запускаются.
До активации также нужны отдельные blind reviews ассистента и пользователя
по 20 различным парам и исходные quality gates обучения из файла 51.
Для подготовки пакетов и отдельного сравнения оценок используется
[оператор blind review](rerank-cohort-review.md), без чтения прогнозов при
выборе пар. Пользовательское авторство файла не выдаётся за проверенную
независимую человеческую оценку.

Повторный пилот использует новые версии pair/suitability prompts, отдельную
cohort identity и общий накопительный ledger. Фактический результат расширения
добавляется после завершения прохода.
