# Индекс поиска и фильтр по вакансии

Витрина принимает `filters.vacancy_id`: UUID опубликованной открытой вакансии
текущего работодателя. API проверяет владельца и исходный статус, matching
повторяет проверку в том же снимке БД, что и поиск. Пригодность вычисляет
существующий `strict_filter` комбайна: класс, пересечение зарплат, формат,
город и явно разрешённый переезд. Чужая или закрытая вакансия недоступна.
Это фильтр пригодности, а не автоматический Like и не ограничение ручного
Like с предупреждением о несовпадении.

Миграция `013_pool_ann.sql` создаёт HNSW для cosine distance над Harrier
`vector(640)`. Семантический канал использует KNN непосредственно по таблице
пула, до оконного ранжирования и RRF. Канал ограничен 200 соседями;
лексический канал сохраняется. `total` относится к объединённой выдаче,
а не к числу всех потенциальных семантических совпадений.

Пулы до 1000 пригодных записей сортируются точно. Для больших используется
`ef_search=400`; если фильтрация оставила недостаточно ANN-результатов,
выполняется точный ограниченный поиск. Согласия, актуальность профиля и
строгие ограничения всегда проверяются независимо от приближённого порядка.
ANN не заменяет полный основной скоринг комбайна: его рейтинг и строгие
координаты остаются точными.

У ANN-запроса локально отключён sequential scan, затем прежняя настройка
возвращается: это явный выбор алгоритма для больших пулов, а не глобальная
настройка PostgreSQL. Проверки пригодности и точный fallback сохраняют обычный
планировщик. Из 400 предварительных соседей в семантический канал допускаются
до 200 уже проверенных записей.

Локальная проверка `test_showcase_ann_integration.py` на 15 001 синтетической
записи показала использование HNSW в `EXPLAIN ANALYZE`, recall@100 = 1,0
и 2,64 мс для запроса 400 соседей. Это результат одного контролируемого
набора; качество и задержка на реальных данных отдельно не измерены.

Курсор привязан к работодателю, фильтрам, ревизии вакансии, пулу и режиму
поиска. Изменение источников требует повторить поиск (`409`).

Историческая миграция `011_hypothesis_exploration.sql` переименована в `012`.
SQL не изменён. Runner сверяет старую контрольную сумму, добавляет
каноническую запись без повторного исполнения и сохраняет историческую.
Повторяющиеся числовые версии новых файлов отклоняются до выполнения SQL.
