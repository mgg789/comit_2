# Недельные рекомендации кандидату

Результат доступен только своему кандидату через `GET /api/candidate/recommendations/latest`: `{item: null | CandidateRecommendation}`. Идентификатор берётся из действующей candidate-сессии. Ответ не кешируется; чужой идентификатор в запросе не принимается.

`week_start` — понедельник UTC недели генерации. Источники покрывают предыдущие семь суток. `state`: `ready` (проверенный ответ DeepSeek), `insufficient_data` (нет достаточно независимых наблюдений), `provider_unavailable` (ограниченные попытки исчерпаны; опубликованы общие подсказки по фактическим агрегатам). Последние два состояния не выдаются за ответ LLM.

## Источники и приватность

API читает employer-отказы `recruitment_processes.closure` (`actor=employer`, `state=rejected`) и завершённые неудачные интервью `recruitment_interviews.feedback`. Выбранные категории находятся в `closure.categories` / `interviews.reason_categories`. Для старого свободного текста используется консервативный локальный словарь явно отрицательных формулировок. Повторы процесса и одного работодателя не усиливают причину. Категория выводится только при минимум трёх разных процессах **и** трёх работодателях. Сырые отзывы остаются в participant store и не передаются ни matching, ни DeepSeek.

Matching сохраняет только реальные решения каждого кандидата при успешной публикации combine/rerank. Общие `run.filter_counts` никогда не используются как причины отдельного кандидата. Категория доступна внутреннему API только после наблюдений в более чем трёх разных вакансиях. Повторные запуски одной вакансии не увеличивают счётчик.

`main_top_k_omission` означает прошедшего строгий фильтр кандидата вне основного top-k. `unranked_by_reranker` появляется только после успешной публикации rerank: кандидат из хвоста main top-k не оценивался reranker. `reranker_reserve` — резерв выдачи. Ни одна из этих категорий не доказывает дефицит навыков. `system_fallback` и `strict_schema_mismatch` явно описываются как системные ограничения.

DeepSeek получает только `{evidence:[{source,category,count}]}` с фиксированными категориями. Имена, IDs, компании, города, контакты, профиль и произвольный отзыв не входят в prompt. Внутренние транспортные заголовки идентифицируют владельца только сервисам. Ответ проверяется по длине, JSON-контракту и допустимым ссылкам на категории; URL, email и UUID отвергаются. Проверка текста не доказывает истинность каждого предложения: prompt запрещает выдумывать причинность, оценки и конкретные навыки.

## Согласие и хранение

Нужны актуальные `processing`, `pool` и явно включённое `training` согласие. API проверяет исходную revision/согласие перед каждым внешним вызовом; agents-service проверяет источник до и после DeepSeek. Финальное сохранение блокирует исходный профиль, проверяет revision и ещё действующую lease. Провайдер вызывается вне SQL-транзакций.

Триггер миграции API `015_candidate_recommendations.sql` сразу удаляет очередь и результаты при отзыве любого требуемого согласия; также удаляет matching-наблюдения, если таблица существует. Matching подключает удаление к существующему `LearningStore.withdraw`. Данные старше 90 суток удаляются worker-ом/публикацией matching. Короткий неизбежный промежуток между последней проверкой согласия и сетевым запросом не устраняет проверки: отозванный результат не сохраняется.

## Очередь и запуск

`CandidateRecommendationsStore.enqueueCurrentWeek()` создаёт одну запись на кандидата/неделю. Уникальность обеспечена PostgreSQL. `WeeklyRecommendationWorker.processOnce()` использует `FOR UPDATE SKIP LOCKED`, lease 300 секунд, максимум три попытки и backoff 30/60 секунд. Истёкшая третья lease публикует честный fallback без четвёртого вызова провайдера. Сохранение и системное уведомление могут выполняться одним коммитом через `notifyInTransaction(client,candidateId,item)`; ключ уведомления должен быть `recommendation:<recommendation_id>`.

Применить обычные API-миграции и matching-миграцию `017_candidate_recommendation_evidence.sql`. Отдельный worker: `pnpm --filter @comit/api exec tsx src/recommendations/worker.ts`. Переменные: `DATABASE_URL`, `MATCHING_ENGINE_URL`, `CANDIDATE_PIPELINE_TOKEN`, `AGENTS_SERVICE_URL`, `AGENTS_SERVICE_TOKEN`. DeepSeek использует существующий `DeepSeekClient` и конфигурацию agents-service. Standalone CLI и API-обвязка публикуют короткое системное уведомление в той же транзакции, с переходом к статистике кандидата.

Внутренние контракты: `GET /internal/candidates/{candidate_id}/recommendation-evidence?after=<UTC>&before=<UTC>` (matching token и совпадающий `X-Owner-ID`); `POST /internal/candidate-recommendations/generate` (agents token и `X-Owner-ID`). Последний возвращает `{text,referenced_categories}`. Все ошибки провайдера приводят к ограниченным попыткам, без вывода credentials или participant prose в логи.

Проверки без живых платных запросов: `pnpm --filter @comit/api exec tsx --test tests/recommendations.test.ts`; `pytest services/matching-engine/tests/test_recommendations.py`; `pytest services/agents-service/tests/test_recommendations.py`. PostgreSQL-acceptance выделен в `recommendations.pg.test.ts` и запускается только с явно указанным изолированным `RECOMMENDATIONS_TEST_DATABASE_URL`. Для включения реального matching-acceptance дополнительно задать `MATCHING_TEST_PYTHON` — путь к Python с установленными зависимостями matching-engine.

Недельные рекомендации требуют нового явного согласия `training-v2`. Версия
`training-v1` совместима с прежним ранжированием, но не включает рекомендации.
Миграция API `017_recommendation_consent_version.sql` расширяет допустимые версии
и очищает результаты без нового согласия. Обновления резюме сохраняют выбранную версию.

Текст для кандидата состоит из коротких понятных советов, без названий внутренних
этапов и категорий. Ответ DeepSeek с такими терминами не публикуется; резервные
подсказки также используют обычный язык. Зарплатное несовпадение не является
оценкой навыков и не требует автоматически снижать ожидания.

Советы учитывают обратную механику Comit: кандидат редактирует профиль и готовится
к разговору, а не отправляет отклики. Текст не должен добавлять зарплату, город,
формат работы или специализацию, если соответствующей причины нет во входе.

Исторические наблюдения не подтверждают, что поля текущего профиля пусты: рекомендации предлагают проверить предпочтения, а не утверждают отсутствие данных. `unranked_by_reranker` означает отсутствие повторной оценки, а не отрицательный результат оценки. Практическая локальная проверка — [отчёт](hiring-live-acceptance.md).
