# Проверка предпочтений вакансии

Реализован слой [файла51, §§4–5](../context/51-reranker-and-feed-learning.md):
сопоставимые проверочные/контрольные карточки в обычной backend-ленте.
Все обязательные фильтры, R₀ и Harrier сохраняются. Реакции поступают в
[существующий learner](preference-learning.md); вывод по гипотезе не создаёт
фильтр и не учитывает тот же лайк второй раз.

## Планирование

Исследование включено по умолчанию. На18 уникальных обычных доставок разрешена
одна пара из2 карточек: верхняя доля резервирования10%. Отменённая/незавершённая
пара также расходует бюджет. Доставка и viewport acknowledgement разделены;
отсутствие решения не получает метку. Pause и rollback предпочтений выключают
новые назначения. Retry/read-back страницы не выбирают новую пару.

Immutable main snapshot повторно проходит strict filters, current revision,
selection state и согласие API/matching. Участники могут находиться в main top-k,
reserve или вне top-k. Признаки и R₀ score вычисляются теми же builders;
outside samples получают `sample_scope=exploration`, main counts не меняются.
Research reserve может появиться при `include_reserve=false`: флаг регулирует
обычную выдачу резерва; исследование имеет отдельные pause/resume.

Попытка ограничена5000 snapshot-кандидатами и200 лучшими допустимыми непоказанными
входами для сопоставления. Ограничение явно даёт `complete=false`; это не
доказательство исчерпания пула. Нет одобренного совместимого R₀/пары — обычная
лента продолжается. Повтор поиска не чаще следующего блока18 обычных доставок.

Пара требует контраста и ограниченных посторонних отличий. Приоритет учитывает
covariance локальной модели (или cold prior), влияние контраста на остаток,
качество сравнения и потерю полезности. Пара выбирается пропорционально приоритету
из bounded feasible set; порядок test/control имеет вероятность0.5.
Вероятности, draw, pool/feature hashes, контраст и preference version фиксируются
до доставки одной транзакцией. Feasible probability support и выбранный index
позволяют воспроизвести draw. Карточка содержит направление и пороги проверки;
числовые различия участников находятся только в удаляемом registry payload.

`selection_probability` относится к паре **при данном feasible set и бюджетной
возможности**; `order_probability=0.5` — к её порядку. Это не вероятность показа
человека из всего пула. Global `propensity=null`: произвольная IPS/causal оценка
полного подбора не поддерживается. Экспорт сохраняет условные вероятности и scope.

Доставленные cards/receipts/позиции не меняются. Пара занимает ближайшие unserved
slots; добавленные извне кандидаты получают новые slots. Обычные карточки не
теряются. Частично доставленная пара закреплена при preference refresh.
Доставка18-й карточки может подготовить пару и вернуть следующий cursor даже
после конца main top-k. Пополнение обычного буфера из §6 остаётся отдельным этапом.

## Контрасты

H1–H8/H10 используют явные доступные признаки и типизированные факты. H5 берёт
максимальную явную длительность experience, не сумму пересекающихся работ.
H6 требует явной эксплуатации против `production_support=false` и developer;
отсутствие факта не означает отсутствие практики. H10 требует совместимого
Harrier и близкого hard-профиля. Уровни и подтверждения отделены.

**H9 выключена** до появления явной таксономии переносимых навыков/соседних
технологий. Соседство не выводится из текста/LLM. Class-only, неизвестные навыки,
отсутствующие факты и несовместимая семантика выключают соответствующие проверки.

## Вывод

Test like/control dislike — свидетельство за; обратное — против. Like/like,
dislike/dislike и незавершённые пары не определяют направление. Кандидат участвует
в research один раз; учитываются только действительные owner/context пары.

До20 решающих пар статус `unclear`. Первая партия20 фиксируется по времени
завершения реакций, в транзакции последнего решения без ожидания запроса статуса;
поздние счётчики обновляются отдельно от сохранённого вывода. Wilson-интервал имеет поправку Bonferroni на10 семейств.
`supported`: нижняя граница>0.5; `not_supported`: верхняя<0.5. Поздние реакции
остаются в журнале и учат learner, но не открывают повторную проверку партии.
Источник формул: [NIST Wilson](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm),
[NIST Bonferroni](https://www.itl.nist.gov/div898/handbook/prc/section4/prc463.htm).

Пороги contrast≥.15, nuisance mean≤.15/component≤.25, utility loss≤.35,
min20 и протокол — **uncalibrated_baseline**. Wilson приближённый; сопоставимость
и случайный порядок не устраняют скрытые различия людей, перенос во времени
и selection bias. Это локальное свидетельство, не доказанная причина выбора.

Контекст включает vacancy/schema/main/R₀/approval/source и preference reset epoch.
Смена контекста/ревизии участника/согласия инвалидирует пару. Отзыв удаляет
параметры и payload вывода, сохраняя хеши и audit. Отозванная fixed batch остаётся
`invalidated`, не заменяется поздними примерами; новая проверка требует reset.

## Управление

- `GET /api/employer/vacancy-drafts/{draft_id}/hypotheses` —10 сводок и scope поиска.
- `POST .../hypotheses/pause` — остановить назначения, завершённые данные сохранить.
- `POST .../hypotheses/resume` — возобновить с прежними бюджетами/контекстом.
- `POST .../hypotheses/reset` — новая epoch и бюджет, старые выводы инвалидировать.

Тело: `PreferenceCommand` с UUID `idempotency_key`, CAS `expected_revision`.
Owner устанавливает API session. Статус без участников, коэффициентов и контактов;
доступен после истечения feed session при текущем контексте. Tinder UI/автоматический
viewport acknowledgement и серверный deployment в этот backend-этап не входят.

## Локальная приёмка

[Отчёт](../data/validation/hypothesis-acceptance.json) сохраняет хеши всех попыток.
Два прогона по22 синтетических профиля с настоящим Harrier640 прошли полный путь:
main top-k18 → research pair вне top-k → replay → две явные реакции → learner/export
→ source-only отзыв согласия и удаление параметров → reset → новая38-я координата
и отклонение устаревшей ленты. Три ранних сценария по40 профилей не дали сопоставимой
пары из-за utility loss>.35; они сохранены, порог не менялся. Ещё одна попытка
остановилась до создания профилей: временный helper передал Node pg libpq DSN
вместо PostgreSQL URI. Всего в этих приёмочных попытках164 профиля, внешних LLM
вызовов0; расход предыдущего teacher и golden не менялись.

Скрипт требует новую пустую loopback PostgreSQL/pgvector БД с именем
`comit_hypothesis_*` и приватную переменную `HYPOTHESIS_ACCEPTANCE_DATABASE_URL`
в формате URI. Скрипт применяет API и matching миграции, оставляет БД/артефакты
для аудита, не очищает старые данные:

```bash
pnpm --filter @comit/api build
PYTHONPATH=services/matching-engine/src services/matching-engine/.venv/bin/python tests/hypothesis_acceptance.py
```

Финальный Python/PostgreSQL прогон:1155 passed,0 skipped; новые policy+PG и
legacy consent regression:27 passed. API запускается последовательно:
`pnpm --filter @comit/api exec tsx --test --test-concurrency=1 'tests/*.test.ts'`
—45 passed, один пропуск внешнего QGramm. Новые API-тесты используют отдельную
`HYPOTHESIS_ROUTE_TEST_DATABASE_URL`; общий parallel fixture truncate ранее
конфликтовал. `pnpm -r typecheck`, `pnpm -r build`, scoped Ruff из корня,
сверка generated OpenAPI и `make smoke`12/12 прошли. Общий Ruff из корня остаётся
красным на34 исторических import-order ошибках; запуск из каталога сервиса
иначе классифицирует импорты, включая два новых теста (подробности в отчёте).

Это проверка механики, не качества предпочтений настоящего работодателя.
Фиксация20 пар проверена отдельными PostgreSQL fixtures до любого GET статуса;
21-я реакция обновляет только диагностику. Эти fixtures не заменяют независимую
разметку или живой эксперимент. Обычный буфер, Tinder и production не проверялись.
