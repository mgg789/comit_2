# Чаты приглашений на QGramm

Внутренний чат открывается после отправки приглашения, до его принятия.
Доступ имеют только авторизованные участники конкретного recruitment-процесса:
работодатель и адресат-соискатель. Предварительный отказ из saved не создаёт
комнату и не становится виден соискателю. Контакты платформа раскрывает через
отдельный endpoint только после принятия приглашения, как описано в
[контуре после like](recruitment.md).

## Состав и хранение

Используется Go-бэкенд [QGramm](https://github.com/mgg789/QGramm), исходники
закреплены полным SHA `f22de87f369cad0b34d243c97ad876a90eb9d6db`.
Минимальный профиль включает только ядро BASIC и `qg_files`. AI, MLS/E2EE,
группы, редактирование, реакции, звонки и федерация не входят в образ.
UI в этом проходе отсутствует.

Приватный Go-адаптер компилируется в модуле QGramm и использует его настоящие
HTTP handlers, SQLite и `cryptoenc`. Ядро не публикует HTTP/WebSocket listener:
браузеры не получают QGramm JWT, ключей устройств, management-секрета,
upload/key/ticket endpoints. Доступ к адаптеру имеет `api-core` по внутреннему
токену. Адаптер принимает только четыре фиксированные операции; свободного
proxy URL нет. Внешний доступ идёт через существующие сессии Comit.

Текст и имена/типы вложений находятся в зашифрованном payload сообщения.
Файлы проходят BASIC-протокол QGramm и шифруются в persistent volume вместе
с SQLite. В PostgreSQL Comit содержимое чатов не копируется. Идентификаторы,
участники, размеры, последовательности и технические метаданные QGramm могут
храниться открыто. Это **серверное шифрование**: сервер имеет возможность
расшифровать сообщения и файлы в памяти. E2EE не заявляется.

## Контракт

Одинаковые маршруты существуют под `/candidate` и `/employer`; nginx добавляет
префикс `/api`. Поля участников берутся только из сессии и БД приглашений.

| Метод и путь после `/{role}/recruitment/{id}/chat` | Назначение |
|---|---|
| `GET /messages?after_sequence=0&limit=50` | История по возрастающей последовательности; `messages`, `next_sequence` |
| `POST /messages` | `{idempotency_key, text, files}` → сохранённое сообщение |
| `POST /files` | `{idempotency_key, name, media_type, data_base64}` → метаданные файла |
| `GET /files/{file_id}` | Опубликованный файл → метаданные и `data_base64` |

Загрузка ограничена 8 MiB исходных байтов, сообщение — 16 000 символов,
вложений — максимум 8. JSON/base64 выбран для backend-прохода; это ограниченный
контракт, большие/потоковые загрузки не реализованы. После загрузки файл ещё
не виден собеседнику: публикация происходит атомарно с сообщением, содержащим
его метаданные. Чужой, неопубликованный или относящийся к другой комнате файл
нельзя скачать/прикрепить. Имена и media type не являются гарантией безопасности
содержимого; будущий UI должен скачивать вложения, а не вставлять HTML в страницу.

UUID `idempotency_key` следует сохранять на время повторов одного запроса.
Изменённый payload с тем же ключом возвращает конфликт. История работает через
polling: клиент сохраняет `next_sequence` после обработки страницы и использует
его в следующем запросе. Пустая страница сохраняет прежний курсор. Push/WS,
read receipts и SMTP-уведомления о сообщениях в этот проход не входят.

Ошибки: `401` — нет действующей сессии нужной роли; `404` — нет доступного
приглашения/файла; `400` — неверный DTO; `409` — конфликт повтора, read-only
процесс или отсутствует processing consent; `413` — превышен размер;
`429` — временно заняты все три chat-слота API;
`503` — чат не настроен, недоступен либо прислал некорректный ответ.
Ответы имеют `Cache-Control: no-store`, service credentials не возвращаются.

## Состояния и сбои

В `sent/viewed/accepted/offer_sent` можно читать и писать. После
`declined/rejected/withdrawn/offer_declined/hired` история и опубликованные файлы
доступны для чтения; сообщения и новые загрузки запрещены. Отзыв согласия
на processing блокирует обе операции; отзыв только pool consent не разрывает
уже начатое общение. Проверка процесса и согласия удерживает DB-locks до конца
ограниченного по времени обращения к адаптеру: изменение статуса/согласия
сериализуется с отправкой/чтением, уже выданных браузерных каналов нет.
Один экземпляр API допускает максимум три chat-операции одновременно и
возвращает остальным `429` с `Retry-After: 1`; это оставляет соединения общего
десятислотового PostgreSQL pool для accounts/profiles и lifecycle.

`chat_available` означает, что backend настроен, процесс приглашён и текущее
согласие разрешает чат. Это возможность обращения, а не обещание доступности
сети: каждый вызов может вернуть `503`. Исторические idempotency receipts
recruitment содержат snapshot времени команды; актуальные флаги читаются через
GET процесса. Недоступность чата не откатывает уже отправленное приглашение.

Комната создаётся лениво при первом обращении. Её идентификатор детерминирован
по UUID процесса; повтор после частичной ошибки повторяет provisioning. Уже
существующая комната принимается только после проверки режима и двух участников.
В PostgreSQL не требуется второе состояние копии комнаты или распределённая
транзакция. При недоступности QGramm API возвращает ошибку, без фиктивной истории.

## Ключи и локальный запуск

Overlay `infra/docker-compose.chat.yml` добавляет приватную сеть и persistent
volume `chat-data`, не публикует порт QGramm и не меняет SMTP. Применяется вместе
с базовым compose и accounts overlay; accounts и profile migrations нужны
из предыдущих проходов. Секреты перечислены в `.env.example`, значения остаются
только в игнорируемом `.env`/secret store. `CHAT_SERVICE_TOKEN` — случайный
токен минимум 32 символа. `CHAT_DEVICE_SECRET`, `CHAT_SIGNING_KEY`,
`QGRAMM_MASTER_KEY`, `QGRAMM_HPKE_KEY` — независимые base64-ключи по 32 байта;
management-секрет также должен быть случайным и достаточной длины.

Ключи устройств принадлежат серверу. Отдельный секрет derivation используется
с разными контекстами процесса/участника; это единая серверная trust boundary,
а не независимые пользовательские приватные ключи. Все эти секреты и volume
нужно резервировать совместно и сохранять при перезапуске. Замена derivation
secret не является ротацией: публичные ключи устройств в QGramm неизменяемы.
Автоматическая ротация/перенос старых устройств этим адаптером не реализованы;
смена storage/HPKE ключей требует штатного протокола QGramm и миграции, не
генерации новых секретов поверх существующей БД.

```sh
docker compose -f infra/docker-compose.yml -f infra/docker-compose.auth.yml \
  -f infra/docker-compose.chat.yml build qgramm-chat api
docker compose -f infra/docker-compose.yml -f infra/docker-compose.auth.yml \
  -f infra/docker-compose.chat.yml up -d qgramm-chat api
```

Во время эксплуатации внешние API/LLM не требуются. Первичная сборка образа
загружает закреплённые исходники и зависимости. QGramm использует один экземпляр
SQLite/local volume; горизонтальный active-active для этого контура не заявлен.

Проверки адаптера находятся в `infra/qgramm/bridge`, сквозная API-проверка —
`apps/api/tests/chat.test.ts` с `CHAT_TEST_DATABASE_URL`,
`CHAT_TEST_SERVICE_URL`, `CHAT_TEST_SERVICE_TOKEN`. Использовать только отдельную
синтетическую БД: тест очищает accounts cascade. Основной контур matching и
найма остаётся независимым от чатов.
