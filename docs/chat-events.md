# Поток событий чата и приглашений

API добавляет SSE без замены существующего polling истории. QGramm остаётся источником сообщений и их durable sequence; приватный bridge отдаёт API только события выбранного процесса. Серверное шифрование и файлы сохраняют прежний контур.

| Endpoint | События |
|---|---|
| `GET /candidate/recruitment/:id/chat/events` | Сообщения конкретного приглашения |
| `GET /employer/recruitment/:id/chat/events` | Те же сообщения для работодателя-участника |
| `GET /candidate/recruitment-events/stream` | Собственные изменения приглашений |
| `GET /employer/recruitment-events/stream` | Собственные изменения процессов найма |

Подключение использует сессию соответствующей роли. Cursor передаётся как `Last-Event-ID` либо `after_sequence`; если заданы оба, они должны совпадать. Разрешены целые 0…9007199254740991. Неправильный cursor даёт 400 до начала stream. Событие содержит `id: <sequence>`, `event: message.created`, JSON `{sequence,type,message}`. `event: cursor` продвигает позицию через скрытые записи QGramm, не раскрывая их данные. Sequence не является количеством видимых сообщений.

Процессные уведомления используют `event: recruitment.changed`, JSON `{sequence,type,event}`. Они приходят из `recruitment_events`, содержат статус и ревизию и не содержат контактов или сообщений. Они доступны без настроенного QGramm. Удаление consent на обработку блокирует чат, но не удаляет собственный журнал статусов приглашения.

При разрыве клиент переподключается с последним **обработанным** cursor. Сервер устанавливает `retry: 1000`, посылает heartbeat и завершает соединение примерно через 60 секунд событием `reconnect` с `after_sequence`. `410 chat_resync_required` до подключения или такое же `event: error` во время потока означает, что нужно перечитать разрешённую историю и восстановить cursor. Будущий QGramm cursor возвращает 400. Приватные ошибки и provider credentials клиенту не передаются.

## Ограничения и права

Для чата каждый короткий poll заново проверяет сессию, участника процесса и текущий consent на обработку. Bridge вызывается с доверенным grant через `withChatGrant`, с таймаутом 5 секунд и отменой при закрытии соединения. Между poll и во время heartbeat DB-соединение не удерживается. Отзыв сессии или consent останавливает stream на очередной проверке. У закрытого процесса остаётся доступ к разрешённой истории; запрет отправки сообщения действует в существующем write-маршруте.

Один API-процесс принимает до 32 SSE-соединений, до двух на аккаунт суммарно для чата и уведомлений, и до трёх одновременных операций с grant/БД, общих с обычными chat-запросами. Превышение даёт 429 и `Retry-After: 1`. Эти семафоры локальны процессу; общий лимит входящих запросов дополнительно использует PostgreSQL. Ответ bridge ограничен 100 событиями и 4 MiB; поля проверяются схемой, порядок sequence и sender проверяются перед доставкой. Backpressure не накапливает страницы; ожидание drain ограничено тремя секундами. Прокси получает `X-Accel-Buffering: no`.

SDK `streamChatEvents()` и `streamRecruitmentEvents()` поддерживает cookie/Bearer и AbortSignal, обрабатывает частично полученный UTF-8 и возвращает cursor при штатном reconnect. Обработчик события может быть асинхронным: cursor продвигается только после его завершения. Автоматического бесконечного reconnect в SDK нет; вызывающий код сохраняет cursor и выбирает политику повторов. Старые `getChatMessages()` и `getRecruitmentEvents()` остаются доступными.

Проверки: `CHAT_SSE_TEST_DATABASE_URL=<disposable-db> pnpm --filter @comit/api exec tsx --test tests/chat-sse.test.ts tests/event-client.test.ts`. Они используют настоящие аккаунты/PostgreSQL и отдельно контролируемый bridge transport для отказов, отзыва consent/сессии и лимитов. Реальный QGramm проверяется отдельным приёмочным запуском.
