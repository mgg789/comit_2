# Дизайн контура тестирования (проект, 09.10.2026)

> Статус на 11.10.2026: реализованы MCQ, короткие ответы, отдельный изолированный
> code broker и Jev/DeepSeek проверка рубрик. Код включается только после реального
> readiness probe, новые рубричные ответы требуют настроенного доступного провайдера. Закрывает блок
> «Механика тестирования, валидация и категоризация» (25% критериев ТЗ §6)
> и превращает testing-engine в trusted producer подтверждённого грейда.
> Канон-контекст: [context/60-testing-engine.md](../context/60-testing-engine.md);
> текущее состояние кода — [testing-engine.md](testing-engine.md); этот документ — целевой дизайн.

## 1. Принцип

Адаптивный тест: до 30 заданий с автопроверкой, сложность следует за
способностью кандидата, сессия заканчивается досрочно, как только грейд
определён уверенно. Результат — `grade_result {status: approved,
test_session_id, approved_at}` в профиль кандидата: подтверждённый грейд
получает коэффициент доверия 1.0 в подборе (против 0.6 у самоотчёта) —
тестирование сразу улучшает подбор, а не существует рядом с ним.

## 2. Банк заданий (MVP)

Семь blueprint-семейств — выбраны по простоте автопроверки:

| Группа | Семейства | Почему |
|---|---|---|
| Домены (3) | `algorithms`, `sql`, `rest_api` | классика автопроверки: код, SQL на встроенной БД, MCQ/рубрики |
| Стеки (3) | `python`, `react`, `docker` | изолированный code-judge исполняет Python; react закрывает фронтенд-крыло (MCQ/чтение кода); docker — дешёвые MCQ |
| Soft skills (1) | `teamwork` | сценарные MCQ + развёрнутые с рубрикой |

Каждое семейство × уровни L1–L4 (границы intern/junior/middle/senior) × варианты.

### Типы заданий и квоты сессии

Ниже целевые доли; текущий код обеспечивает ключевые слоты: для Python и
Algorithms второй вопрос — код, развёрнутый вопрос ставится в выделенный слот
при наличии рубрики и настройки провайдера. Первый вопрос — MCQ или short_answer.

| Тип | Доля сессии | Проверка |
|---|---|---|
| Выбор из 4 | ~50 % | точная, серверная; параметризация + перемешивание опций |
| Код | ~25–30 % | скрытые тесты в песочнице; эталонное решение обязано проходить их до публикации задания |
| Развёрнутый ответ | ~20–25 % (3–5 заданий, tie-breakers на границе грейда) | рубрика с чек-поинтами; детерминированные предчеки (объём, ключевые термины/шаги) → затем LLM-судья |

Граница ответственности (правило «LLM не решает»): LLM-судья оценивает **один
ответ по рубрике**; грейд назначает только алгоритм агрегации сессии.

## 3. Генерация: офлайн-банк с дневным лимитом

- LLM генерирует варианты по шаблонам-параметрам **офлайн-воркером в банк**;
  рантайм сессии не генерирует вопросы. Проверка новых развёрнутых ответов
  вызывает настроенный Jev/DeepSeek; офлайн доступны детерминированные типы,
  локальный изолированный code runner и ранее закэшированные рубричные вердикты.
- **Дневной лимит** — бюджет ledger'ом (паттерн реранкера): кумулятивный
  счётчик `generation/день`, refill-воркер добирает банк до минимального
  запаса (5 неиспользованных вариантов на семейство × уровень).
- Валидатор качества до публикации в банк: код — эталонное решение проходит
  скрытые тесты; MCQ — ровно один защитимый ответ + фильтр похожести против
  существующих вариантов; развёрнутый — рубрика содержит проверяемые ключевые
  пункты.
- **Мораторий экземпляра**: N показов (3) ИЛИ T часов (24) — что раньше;
  в реализации сгенерированные экземпляры выводятся из оборота, seed сохраняются.
  Если все допустимые варианты показаны сегодня, действует fallback с минимальным
  exposure; тип задания и исключения текущей сессии применяются до ротации.

## 4. Адаптивная сессия

- Старт с уровня L2. После каждого ответа — пересчёт способности и постериора
  над 4 грейдами; следующее задание — на границе максимальной неопределённости
  (бисекция; целевая вероятность успеха ~70 %).
- **Ранний выход**: последовательный критерий (SPRT-подобный) — грейд принят,
  когда постериор ≥0.8 и оставшиеся задания не могут перевернуть решение между
  соседними грейдами. Потолок — 30 заданий или исчерпание банка уровня.
  Реализация (`adaptive.py`) сейчас использует порог 0.70 и отставание второго
  грейда более чем в 2 раза.
- Развёрнутые ответы ставятся на границы грейдов как tie-breakers.
  Это целевое правило; текущий слот и ограничения банка описаны выше.

## 5. Паноптикум: наблюдение без записи (по умолчанию)

Два независимых сигнала, всё считается **на клиенте**:

- **Фокус окна**: Page Visibility API → `focus_lost_seconds`, число переключений.
- **Присутствие в кадре**: YuNet (onnxruntime-web, wasm/webgpu, ~2 МБ, CPU) —
  детекция лица и числа лиц прямо в браузере; blazeface — запасной кандидат
  для бенчмарка. Кадры не покидают устройство; наружу — только агрегаты.

YuNet описывает исходный reference-клиент. Текущий `apps/testing/src/media.ts`
использует MediaPipe FaceDetector с локальными WASM/model assets; при выключенной
записи наружу передаются только агрегаты, в режиме `full` — согласованные записи.

Работодатель видит **только бейдж присутствия** (без чисел):

| Бейдж | Условие |
|---|---|
| Хороший | ≥95 % времени в кадре, ноль событий мульти-лица |
| Нормальный | 85–95 % в кадре |
| Средний | 70–85 % в кадре или единичные мульти-лица |
| Низкий | <70 % в кадре |
| Не определён | камера не выдана / модель не запустилась (визуально отличается от «Низкого»: не вина кандидата) |

Отказ от вебки не блокирует тест. Полные счётчики — в операторском отчёте
сессии, не работодателю. «Мульти-лицо» — эвристический сигнал, в доках так и
назван. Детектор «лицо отсутствует» надёжнее «числа лиц» — основной вес в
бейдже у отсутствия.

### Согласия и режим записи (двухдонная конструкция)

- Участник подписывает **согласие на обработку и хранение материалов
  прохождения (видеоанализ) 90 дней для анализа честности** и отдельное
  согласие на **сбор и хранение записи экрана 90 дней**.
- **По умолчанию** — realtime-режим: кадры и экран не покидают устройство,
  хранятся только агрегаты и ответы.
- **Контур полной записи полностью подготовлен и выключен одной переменной**
  (`TESTING_RECORDING_MODE=full`, см. [testing-engine.md](testing-engine.md)): клиент начинает прикладывать носители,
  сервер — складывать их в хранилище с TTL-очисткой на 90-й день. Согласие
  сформулировано так, что покрывает оба режима («может собираться выборочно
  для анализа честности прохождения»). В текущем UI состояние режима явно
  сообщается участнику, формулировки согласий зависят от `recording_enabled`;
  при выключенном режиме прямо указано, что видео не записывается.

## 6. Анти-чит

- **Утренний слив**: параметризация + перемешивание убивают буквальный слив
  («ответ B» бесполезен у следующего кандидата); мораторий экземпляра
  сжигает показанное; дневной refill держит банк свежим. Утечённый метод
  решения неотличим от подготовки, поэтому цель дизайна — малый радиус поражения
  и короткий период полураспада утечки.
- **Пожарный карантин**: аномалия «серия быстрых правильных ответов разных
  кандидатов на одном экземпляре за короткое окно» → экземпляр уходит в
  quarantine (без обвинений кандидатов).
- **Идентичность кода**: нормализованная похожесть (токены/AST) на недавние
  сабмиты + точные дубликаты; флаг в отчёте сессии.
- **AI-детекция** — следующий этап развития дизайна; текущий контур проверки
  рубрик её не использует.

## 7. Интеграция с профилем и подбором

- testing-engine — **trusted producer**: результат сессии уходит внутренним
  контуром в профиль как `grade_result {approved, test_session_id,
  approved_at}` (реализация зарезервированного контракта; browser-канал
  по-прежнему не принимает approved).
- Категоризация: specialization (из профиля) × подтверждённый грейд;
  cooldown пересдачи — 7 дней; подтверждение повышения грейда — не раньше
  30 дней.
- Схема testing-engine: blueprints, items (варианты), sessions, answers,
  proctoring_counters, judge_reports.

Это целевая модель. Текущее хранилище файловое; публикация подтверждённого
семейства не переписывает общий заявленный грейд. Для авторизованного браузера
публикация происходит после `/finish`, когда финализированы материалы.

## 8. Хранение

Сырые ответы и прокторинг-агрегаты: **90 дней** (нужно для валидации:
test-retest, дискриминативность, экспертная сверка), затем агрегаты.
Носители в режиме полной записи: 90 дней, потом удаление (TTL-очистка).
Судейские отчёты (развёрнутые ответы) хранятся рядом с ответом.

Пункт задаёт целевую политику. Реализованная автоматическая TTL-очистка удаляет
носители по manifest; очистка sessions/ответов/рубричного кэша — следующий шаг
развития `maintenance()`.

## 9. Судья развёрнутых ответов

Реализован `testing_engine.rubric.RubricJudge`: настроенный Jev приоритетен,
иначе используется DeepSeek. Рубрика серверная, ответ кандидата передаётся
как недоверенные данные. Принимается только валидный вердикт по каждому критерию;
грейд рассчитывает adaptive engine, а не провайдер. Валидные ответы кэшируются,
недоступность или неверная форма ответа дают повторяемую ошибку без изменения
оценки. Отдельная квота влияния развёрнутых ответов и экспертная калибровка —
следующий этап; параметры и точный контракт — [testing-engine.md](testing-engine.md).

## 10. Валидация (процедура под 25% — сразу в дизайне)

1. **Test-retest**: повторная сессия на новых вариантах тех же blueprint'ов →
   стабильность грейда.
2. **Дискриминативность**: заведомо слабые/сильные синтетические сессии →
   разрыв скорингов (point-biserial).
3. **Экспертная сверка**: N=30 решений вручную vs автопроверка/судья —
   совпадение и калибровка судьи.
4. **Утечка**: демонстрация, что «слитый» экземпляр не даёт преимущества
   следующему кандидату (мораторий + параметризация).

## 11. Фазы

- **P1 (демо-ядро)**: банк 7 семейств + генератор с ledger-лимитом и
  валидатором, адаптивный раннер (MCQ + код + песочница), focus-счётчик,
  запись approved-grade в профиль, cooldown.
- **P2**: YuNet-паноптикум (клиент + бейджи), развёрнутые ответы + DeepSeek-судья,
  контур полной записи за env-переменной.
- **P3**: валидационная процедура + цифры в документацию сдачи.

## Реализация прохода 3 (10.10.2026)

Паноптикум реализован: `supervision.py` — бейдж-математика (пять градаций,
мульти-лицо ограничивает «средним»), bounded-валидация агрегатов (завышенные
счётчики отвергаются), `cleanup_expired_media` (TTL 90 дней). Маршруты:
`POST /testing/sessions/{id}/supervision` (только агрегаты — кадры не покидают
устройство) и `POST /testing/sessions/{id}/media` — контур полной записи,
выключен по умолчанию (`TESTING_RECORDING_MODE=off`), при
`TESTING_RECORDING_MODE=full` требует согласия на запись экрана и хранит
чанки с TTL 90 дней. Согласия (`video_analysis`, `screen_recording`)
фиксируются при создании сессии. Reference-клиент YuNet:
`services/testing-engine/static/proctoring-client.js` (onnxruntime-web,
агрегаты на клиенте). Тесты: `test_supervision.py` (границы бейджа, 400 на
завышенные счётчики, env-гейтинг media, 403 без согласия).

## Валидация выполнена (10.10.2026)

Исторический отчёт `services/testing-engine/tests/validation_suite.py` (suite-режим) содержит четыре
синтетические проверки. Текущий браузерный и judge-контур
проверяется отдельно ([testing-engine.md](testing-engine.md)). Актуальный протокол — `synthetic-multifamily-v2` в
`data/validation/testing-validation.json`: 84 профиля, семь семейств, независимые
ответы в повторе, реальные распределения четырёх грейдов. Старые значения 1.0
по двум идеальным прогонам и крайним классам 3+3 не являются доказательством
калибровки и заменены фактически измеренными значениями. Сожжённые экземпляры
не возвращаются; MCQ имеют сохраняемую перестановку; новый офлайн запас
вычисляется по параметрам, а не дублирует слитый ответ. Проверка ключей не
равна работе экспертной панели, а синтетический test-retest не равен исследованию
на людях. Точные числа и ограничения — в версионированном отчёте.

## Проверка кода и code-judge (актуализация 11.10.2026)

Локальная песочница в testing-engine удалена как RCE-путь (issue #18): код
кандидата проверяет только отдельный сервис `services/code-judge` по
`CODE_JUDGE_URL` с внутренним токеном. Broker выполняет каждый testcase в
одноразовом изолированном контейнере отдельного daemon и сравнивает результаты
снаружи; readiness проверяет реальные ограничения. `LocalPythonJudge` всегда
отключён, включая fixture-флаг. Эталоны генератора идут через тот же broker.
Рубричный Jev/DeepSeek-судья подключён; при отказе проверки вопрос остаётся
доступным для повтора без изменения оценки. Подробности — [testing-engine.md](testing-engine.md).

## Следующие шаги

- Эксплуатация отдельной judge VM и калибровка лимитов на реальных задачах;
  контейнерные ограничения и повтор после отказа уже реализованы.
- Калибровочные пороги уровней L1–L4 на старте — фиксируем после первых

- Стоимость/лимиты DeepSeek-судьи при пиковой нагрузке (дневной бюджет
  judge-вызовов — тем же ledger-паттерном).
