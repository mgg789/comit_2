# Эксплуатационные ограничения API

`apps/api/src/operations/index.ts` устанавливается на корневой Fastify до бизнес-маршрутов. Ограничение распространяется на чтение, запись, публичные и внутренние маршруты, включая запросы без авторизации. Лимиты OTP остаются отдельным, более строгим контуром.

При корректной конфигурации авторизации и `DATABASE_URL` каждый экземпляр API использует общий PostgreSQL-счётчик из миграции `006_api_operations.sql`. Ключ — HMAC адреса клиента с секретом авторизации; исходный IP в таблицу не записывается. Атомарный UPSERT предотвращает обход квоты через несколько экземпляров. При ошибке БД API возвращает `503 rate_limit_unavailable`; перехода на новый локальный счётчик нет.

Без настроенной авторизации работает локальная квота с ограниченным количеством ключей. При заполнении памяти новые адреса получают 429; вытеснения чужой квоты нет. Этот режим не объединяет несколько процессов и предназначен для автономного контура. Клиентский адрес берётся из Fastify `request.ip`; `TRUST_PROXY` следует задавать только для доверенных прокси.

Настройки:

| Переменная | По умолчанию | Значение |
|---|---:|---|
| `API_RATE_LIMIT` | 240 | Запросов на IP за фиксированное окно |
| `API_RATE_WINDOW_SECONDS` | 60 | Длительность окна, секунды |
| `API_RATE_FALLBACK_KEYS` | 10000 | Максимум адресов в локальном режиме |

Положительные целые обязательны. При превышении квоты возвращаются `429 rate_limited` и `Retry-After`. `/healthz`, `/ready`, `/metrics` исключены, чтобы диагностика оставалась доступной. Фиксированное окно допускает два последовательных бюджета на его границе; это не скользящее окно. Общая квота по IP может объединять пользователей за NAT, поэтому её следует настраивать для реальной нагрузки.

## Корреляция и метрики

`X-Request-ID` принимается только как строка из 1–64 безопасных ASCII-символов; иначе генерируется UUID. Значение возвращается клиенту. `correlatedFetch` передаёт его приватным сервисам, сохраняя собственные доверенные заголовки адаптера. AsyncLocalStorage разделяет параллельные запросы. Публичные account/showcase-адаптеры и зависимости `authDomain` используют этот транспорт.

`GET /metrics` отдаёт Prometheus text format: количество запросов, гистограмму времени, количество отказов квоты и ошибок её хранилища. Единственные метки запроса — метод и класс HTTP-статуса. Адресов, email, UUID пользователей/вакансий, текста поиска, токенов и URL в метках нет. Метрики локальны одному процессу; Prometheus должен собирать каждый экземпляр. Endpoint не требует пользовательской сессии и раскрывает только агрегаты.

Миграции применяются явной командой `pnpm --filter @comit/api auth:migrate` перед запуском. Сервинг не меняет схему автоматически.

`createApiServer()` собирает полный production-граф маршрутов без открытия listener. CLI `src/server.ts`/`dist/server.js` вызывает эту же фабрику и затем слушает `PORT`. Проверка `pnpm --filter @comit/api exec tsx --test tests/server-registration.test.ts` регистрирует вместе matching, agents, auth и все публичные маршруты; она обнаруживает конфликты namespace, которые изолированные plugin-тесты не покрывают.

Проверки: `OPERATIONS_TEST_DATABASE_URL=<disposable-db> pnpm --filter @comit/api exec tsx --test tests/operations.test.ts` проверяет конкурентную корреляцию, локальную квоту, общий лимит двух API, отказ БД и отсутствие приватных меток.
