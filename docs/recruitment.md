# Контур после like

Уточнение Mike от 06.10.2026: **like → saved → приглашение → предложение
соискателю → принятие → контакты, собеседования, оффер или отказ**.
Внутренний чат разрешён уже на стадии приглашения, до раскрытия контактов.
Отдельный backend-проход реализует [чаты и файлы на QGramm](chat.md).
Кабинеты кандидата и работодателя показывают процессы и чат ([candidate-ui.md](candidate-ui.md), [employer-ui.md](employer-ui.md)); без настройки QGramm API возвращает `chat_available:false`.

## Владелец данных и границы

`api-core` хранит hiring aggregate пары owner/vacancy/candidate. Matching
продолжает владеть like/saved/attractive и их историей: API не меняет score,
вектора или правило N>K. Работодатель читает saved и список recruitment;
по candidate_id объединяет их, чтобы отличить ещё не обработанных кандидатов,
приглашённых и завершённые процессы. Историческое like не удаляется при отказе;
attractive продолжает исключать эту пару из комбайна. Новые приглашения для
уже существующей пары запрещены, включая завершённый процесс. Явное
возобновление — следующий отдельный контракт, не автоматический N>K.

Для отправки требуется принадлежащая работодателю опубликованная вакансия,
saved-членство, актуальный liked exposure и source/profile projection ACK.
Matching предоставляет точечный owner-scoped `GET /saved/{candidate_id}`.
При создании API держит account/profile locks до commit и повторно проверяет
processing/pool consent и точный ACK. Приглашение фиксирует разрешённый снимок
и условия; дальнейшее изменение вакансии или снятие pool consent не отзывают
уже отправленное приглашение. Общей распределённой транзакции с engines нет.
Saved — durable grant: в данном контуре решение сохраняется без операций unlike/delete.

Название компании берётся из профиля работодателя (`GET/PATCH /employer/profile`): без него приглашение отклоняется с 409 `employer_company_required`, а переданный `company_name`, отличный от сохранённого, — с 409 `employer_company_mismatch`. Название указывает сам работодатель; проверка компании — отдельный следующий этап.
Описание и обязательная зарплата от–до видны соискателю до принятия. Если salary
опущена, берётся диапазон опубликованной вакансии. Название, город, daily и
формат также фиксируются; отправленное предложение неизменно, а редактирование после отправки — возможное расширение.

## Состояния и действия

| Состояние | Работодатель | Соискатель |
|---|---|---|
| sent / viewed | Отклонить | Просмотреть, принять или отклонить |
| accepted | Предложить/отменить/завершить собес, отправить оффер, отклонить | Принять/отклонить время, выйти из процесса |
| offer_sent | Собеседования остаются доступны, отклонить | Собеседования, принять/отклонить оффер, выйти |
| hired / declined / rejected / offer_declined / withdrawn | Новые переходы запрещены | Новые переходы запрещены |

Ответ возвращает вычисленные `allowed_actions`, отдельные interviews/offers,
revision и историю результатов. Общие карточки, процесс и events не содержат
контактов. Только `GET /employer/recruitment/{id}/contacts` открывает текущие
имя/email/phone после принятия (accepted/offer_sent/hired), своему работодателю,
при действующем processing consent. Pool consent управляет будущим поиском:
его отзыв после приглашения не блокирует существующий процесс. Отзыв processing
немедленно закрывает контакты и новые положительные действия; отказ/выход/отмена
и доступ к собственной истории сохраняются. Все ответы `Cache-Control:no-store`.

Отказ до отправки приглашения создаёт employer-only rejected-запись с
`terms:null` и `invited_at:null`: соискатель не видит попадания в shortlist,
этого отказа, его причины или события. Отказы после приглашения требуют причину,
сохраняют видимую обеим сторонам `closure` и закрывают процесс. Внутренний
короткий отказ не выдаётся за отправленное приглашение.

## Собеседования

Максимум один **проведённый** technical и один general на процесс. Для каждого
типа существует только один proposed/scheduled/completed slot; DB unique index
и process lock защищают лимит при двух вкладках. Отмена/отклонение времени не
расходуют слот, новое назначение создаёт отдельную запись, история сохраняется.
Перенос: отменить старую запись, предложить новую. Другие виды собеседований
и повторные раунды — следующие расширения контура.

Работодатель задаёт абсолютное starts_at, IANA time_zone, длительность1–480мин,
remote/onsite и URL/адрес. Соискатель подтверждает либо отклоняет время.
Предложение и его принятие допускаются только до starts_at. Прошедший proposal
можно отменить. Проведение отмечает работодатель не раньше starts_at; outcome
passed/failed/neutral и feedback обязательны. Failed не означает автоматический
отказ. После двух completed остаются оффер или отказ. Meetings не создают
звонок, календарный event или отправку на внешний URL.

## Оффер, время и идемпотентность

Оффер доступен сразу после принятия приглашения, независимо от собеседований.
Нужны точная зарплата в целых RUB>0, описание условий и expires_at. Одновременно
один sent offer. Принятие → hired; отклонение → offer_declined. Завершение
процесса отменяет незавершённые встречи и закрывает outstanding offer, сохраняя
записи. Принятие оффера не меняет бизнес-статус вакансии.

При `expires_at <= clock_timestamp()` оффер expired, процесс возвращается в
accepted и можно отправить новый. Expiry фиксируется лениво на get/list и перед
action, под process lock, отдельным revision/event. Позднее принятие запрещено
также SQL-предикатом непосредственно при записи. Invites без автоматического
срока, no-show/SLA/напоминания в этот проход не входят.

Каждый action требует expected_revision и UUID idempotency_key. Старый revision
даёт409. Ключ имеет область actor_id + key, fingerprint включает путь и весь
command: конфликтующий payload даёт409. Повтор возвращает исходную contact-free
receipt даже после смены источника или недоступности engines; для текущего
состояния клиент отдельно делает GET. Один process на owner/vacancy/candidate.

## События и проверка

Изменение process, receipt и event пишутся одной транзакцией. Event содержит
только id, глобальный sequence, process_id, revision, type, state и created_at;
нет контактов, условий, причин, meeting URL или model output. Participant polling
возвращает only-own events, `next_sequence` и `has_more`; потребитель дедуплицирует
event_id. Вставки сериализованы до commit, чтобы курсор не пропустил lower
uncommitted sequence. События не удаляются автоматически. Email о собеседованиях
([email-notifications.md](email-notifications.md)) и чат ([chat.md](chat.md))
реализованы отдельными контурами и этот журнал не потребляют; consumer leases и
WebSocket для него — возможные расширения.

Запуск API SQL: `pnpm --filter @comit/api auth:migrate`; сервер не мигрирует сам.
Тесты API: `pnpm exec tsx --test --test-concurrency=1 tests/*.test.ts` из apps/api
с явными отдельными AUTH/PROFILE/RECRUITMENT test database env.
Реальный HTTP: `python tests/recruitment_acceptance.py` с
RECRUITMENT_ACCEPTANCE_DATABASE_URL и локальными API/MATCHING/AGENTS URLs.
Приёмка требует пустую отдельную `comit_profile_acceptance_recruitment*` БД и
использует настоящие auth/projection/Harrier/PDF/main/R0/like и обе hiring ветки.

См. [API](api.md), [данные](data.md), [контекст](../context/30-domain-model.md).

## Сроки и трудоустройство — 10 октября 2026

Сроки хранит API, сверка выполняется каждые пять секунд и при чтении/действии. Один рабочий день — 24 часа понедельника–пятницы в `Europe/Moscow`; суббота и воскресенье не расходуют время. Праздники отдельным календарём не исключаются. Оба участника получают одинаковый `deadline` и системные уведомления, UI только показывает оставшееся рабочее время.

| Событие | Следующий срок работодателя |
|---|---|
| Кандидат принял приглашение | 4 рабочих дня; на третий день одно напоминание |
| Первое успешно доставленное сообщение работодателя | 7 рабочих дней; повторные сообщения не продлевают срок |
| Предложено собеседование | 7 рабочих дней на согласование; неподтверждённое время не снимает срок |
| Кандидат подтвердил собеседование | Пауза до запланированного окончания встречи |
| Время согласованной встречи закончилось | 3 рабочих дня на оффер или отказ; ручное завершение не требуется |
| Отменено/отклонено время встречи | Пауза до другой согласованной встречи, иначе 7 рабочих дней |
| Отправлен оффер | Срок ответа определяется `offer.expires_at`; работодателю новый таймер не показывается |
| Истёк оффер | Возврат в accepted, 7 рабочих дней |
| Вакансия закрыта/отозвана или согласие на обработку профиля отозвано | Таймер приостановлен; после восстановления и чтения процесса — 7 рабочих дней |
| Срок действия работодателя истёк | Terminal `expired`, `closure.actor=system`, одно событие `deadline.expired` |

Сверка, пользовательское действие и успешная доставка сообщения блокируют один aggregate. Просроченное действие не откатывает уже истёкший срок. Повторы idempotency key возвращают прежний результат. Встреча, отмена и результат остаются отдельными записями; только согласованная встреча приостанавливает ожидание. При двух встречах учитывается последнее время окончания.

При employer reject, в том числе до приглашения, обязательны минимум 80 символов после trim, 10 слов и 1–7 уникальных категорий `technical_skills|experience|communication|salary|work_format|location|other`. Такие же требования применяются к отрицательному результату собеседования. Полный текст доступен участникам; системные уведомления его не копируют. До приглашения отказ остаётся внутренним.

Принятие оффера кандидатом, а не отправка работодателем, означает `hired` в текущем продукте. В той же транзакции добавляется опыт с ID процесса, сохраняются остальные поля и согласие обработки, снимается pool consent, создаётся точный снимок projection outbox и уведомление Comit. Повтор не создаёт второй опыт. Новый опыт является заявленным фактом, не подтверждённой внешней верификацией. Готовность matching к отзыву проверяет исходную ревизию даже до доставки очереди.

Компания принадлежит профилю работодателя: [профиль и inbox](system-inbox.md). До заполнения компании приглашение возвращает `409 employer_company_required`; старое поле `company_name` допустимо только при совпадении с профилем. Ранее отправленные terms не меняются после переименования компании.

Недельные рекомендации и ограничения обезличивания: [recommendations.md](recommendations.md). Проверки календаря, гонок и трудоустройства: `pnpm --filter @comit/api exec tsx --test tests/recruitment-deadlines.test.ts`; PostgreSQL часть запускается только в явно изолированной локальной БД `hiring_test_*` через `RECRUITMENT_DEADLINES_TEST_DATABASE_URL`.

Принятие оффера также выключает зависимое согласие на обучение/рекомендации и
очищает его отметку: оно допустимо только при участии в пуле. Согласие на обработку
сохраняется. Это предотвращает нарушение ограничения БД для профиля с training-v2.


## Сверка старых процессов и доступность чтения

У старого `accepted` без `deadline` первый расчёт начинает полный срок с серверного времени первой сверки, а не с `updated_at`. Предложенная встреча, `employer_contacted_at` или сохранённое событие первого сообщения дают 7 рабочих дней; прошедшая согласованная/завершённая встреча — 3 дня; будущая согласованная встреча сохраняет паузу до её окончания. Если старое внешнее сообщение не оставило локального события, его наличие не выдумывается: действует новый полный начальный срок. Уже завершённые исторические процессы автоматически не восстанавливаются.

Чтение карточки и списка запрашивает authority до транзакции PostgreSQL. На странице одна и та же вакансия проверяется один раз; разные вакансии проверяются группами максимум по четыре. После ошибки источника или исчерпания общего 10-секундного бюджета старта запросов остальные группы переходят в безопасное состояние без новых запросов. При недоступном источнике история возвращается, чат доступен только для чтения, остаются действия выхода; ошибка источника сама по себе не меняет и не приостанавливает сохранённый таймер. Переходы вперёд и отправка сообщения всё равно проверяют источник заново под блокировкой и запрещены при его сбое.

Закрытая/отозванная вакансия сохраняет допустимые для стадии выходы: отказ от приглашения/оффера, выход кандидата, отказ работодателя с обязательной ОС, отмена/отказ от встречи. Правка текста опубликованной вакансии не замораживает существующий найм: учитывается последняя принятая публикация (`published_at`) при `business_status=open`. Старой даты недостаточно после более позднего отзыва — новая публикация должна быть принята. Локальная операция закрытия, завершившаяся во время удалённой проверки, имеет приоритет над её устаревшим положительным ответом.

Регрессии: `apps/api/tests/recruitment-authority.test.ts`, `recruitment-deadlines.test.ts`, `recruitment-store.test.ts`, `recruitment-cursor.test.ts` на одноразовой PostgreSQL-базе.

## Почему нет самостоятельного отклика

Самостоятельный отклик кандидата на вакансию исключён сознательно: это продуктовое
решение обратной механики, а не пробел контура найма. Обоснование и рычаги кандидата
вместо отклика — [inverse-concept.md](inverse-concept.md).
