# Черновик вакансии и агент заполнения

Ручная форма и чат редактируют **один** черновик в `agents-service`.
UI и аккаунты в этот проход не входят. `owner_id` — UUID для учёта владельца;
он не подтверждает личность. Вызовы доступны доверенным сервисам с
`AGENTS_SERVICE_TOKEN` и `X-Owner-ID`; токен нельзя отдавать браузеру.

## Путь создания

1. Создать черновик, заполнить или изменить поля через PATCH либо инструменты чата.
2. `approve` проверяет поля и сохраняет summary текущей ревизии. Дополнительного
   согласования отдельных изменений или самого approve нет.
3. Человек читает summary. Правка возвращает черновик в `editing`, удаляя старое
   summary. `Создать` передаёт `expected_revision` и `summary_hash`, подтверждая
   именно показанный снимок.
4. Транзакция замораживает данные и ставит publication job. Worker отправляет
   полный `VacancyInput` в matching intake с `status=open`.
   `vacancy_id=draft_id`, `source_revision=summary.revision`, `metadata.title`
   содержит название. Повтор Create возвращает ту же публикацию.
5. Intake ACK переводит черновик в `created`: это **принятие входных данных**.
   Техническую готовность следует читать через `/pipeline`. Вектора строит
   существующий vacancy worker; событие `vacancy.ready` поступает существующему
   комбайну. Реранкер и его веса этот сервис не меняет.

Для approve обязательны название, обе зарплатные границы в RUB, график `daily`,
город, формат `onsite|remote|hybrid`, а также класс **или** хотя бы один домен/стек.
Описание и каждая группа навыков могут быть пустыми. Одних soft skills недостаточно.
Уровни — целые `0..7`; отсутствие навыка отличается от явно заданного `0`.
Ключи групп берутся из действующего строгого реестра matching-engine.

Редактирование использует CAS по ревизии для защиты от одновременной записи формы
и старого ответа агента. После Create снимок заморожен, включая ошибку отправки;
для ошибки есть retry job. Изменение опубликованной вакансии — отдельный поток.

## Два способа заполнения

Ручной PATCH работает без внешних моделей. Для автозаполнения трёх групп форма
может вызвать `/enrich`. Worker обращается к локальному jev-local,
`POST /api/v1/decisions`, модель `aac6fef/laya-multilingual-mlx`. Для каждой
координаты используется 9 вариантов: отсутствует и уровни 0–7. Выбирается максимум
вероятности, а не округление ожидаемой оценки. Пакеты содержат не более 24 вопросов.
Сохраняются модель, версия рубрики, hash исходных полей и реестра, вероятности.
Ручные и агентские правки групп имеют приоритет над повторной Laya-деривацией.
Результат устаревшей ревизии не применяется. Это редактируемое заполнение требований,
а не решение о найме; качество оценок требует продуктовой калибровки.

Чат имеет прямой доступ к реестру и тем же полям. Он **не вызывает jev**.
DeepSeek подключается через HTTPS `/chat/completions`, модель из env;
проверочный провайдер — `deepseek-flash`, thinking отключён. Используется
[официальный протокол tool calls](https://api-docs.deepseek.com/guides/tool_calls/).
Инструменты: чтение черновика/реестра, изменение полей, approve и типизированные
интеракции. Инструмента Create/publish у агента нет: он заканчивает на summary.
DTO кнопок, выборов и slider доступны будущему клиенту без реализации UI.

## Хранение и восстановление

Отдельная PostgreSQL-схема `agents_service` хранит editorial drafts, immutable
summary, jobs, сессии, сообщения, provider cache и журнал инструментов. Matching
владеет опубликованной проекцией, векторами и событиями отбора.
Миграции запускаются явно, проверяются по checksum; сервер сам их не применяет.

Jobs используют leases, heartbeat, ограниченные попытки и backoff. Внешний вызов
проходит вне SQL-транзакции; результат сохраняется до применения инструментов.
Повтор инструмента определяется `(turn_id, call_id)`; его эффект и журнал
фиксируются одной транзакцией. Кэш ограничен владельцем и hash запроса.
Ошибки провайдера видны как безопасные коды; фиктивных ответов/навыков нет.

Знания — Markdown и определения в пакете сервиса. Их hashes фиксируются в сессии;
несовместимое обновление не меняет инструкцию запущенного turn незаметно.
Лимиты: до 8 раундов, 16 tool calls, 1536 выходных токенов на вызов, 16000 токенов
учтённых провайдером токенов на turn и 24000 символов контекста. Лимит проверяется
после ответа; последний вызов может превысить его за счёт входных токенов.
Ответы инструментов содержат поля и состояние без повторения журнала вероятностей.
При сокращении контекста актуальный черновик
остаётся источником состояния; история не заменяет поля.

## Запуск и проверка

```sh
cd services/agents-service
python -m pip install '.[dev]'
python -m agents_service migrate
python -m agents_service serve
python -m agents_service worker
```

Env: `DATABASE_URL`, `AGENTS_SERVICE_TOKEN`, `MATCHING_ENGINE_URL`,
`CANDIDATE_PIPELINE_TOKEN`, `JEV_LOCAL_URL`, `DEEPSEEK_BASE_URL`, `DEEPSEEK_MODEL`,
`DEEPSEEK_API_KEY`. Секреты передаются процессу/контейнеру извне.
Для Docker используется opt-in overlay `infra/docker-compose.agents.yml` после
`docker-compose.candidate-pipeline.yml`. Laya остаётся локальным host-сервисом;
в контейнере нет MLX. Jev слушает loopback: доступ из контейнера зависит от
топологии Docker/хоста. При недоступности enrich показывает ошибку,
ручное заполнение продолжает работать. Не открывать jev наружу ради этого потока.

```sh
PYTHONPATH=services/agents-service/src python -m pytest services/agents-service/tests
ruff check services/agents-service/src services/agents-service/tests
PYTHONPATH=services/agents-service/src python tests/generate_agents_contract.py
pnpm --filter @comit/api test
pnpm -r typecheck
./tests/smoke.sh
```

PG-тесты требуют `AGENTS_TEST_DATABASE_URL` с **отдельной одноразовой** БД: тесты
очищают только схему agents_service. Реальные модели проверяются отдельно от
unit-тестов; `/healthz` не доказывает корректность provider workflow.
