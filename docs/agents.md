# Агенты работодателя и редакционный контур вакансии

`DraftView` включает nullable ISO-8601 даты `created_at`, `published_at`, `closed_at`.
Создание берётся из неизменяемого времени записи; публикация — из успешного
подтверждения публикации worker; закрытие — из явного действия владельца.
Миграция `009_vacancy_dates.sql` восстанавливает известные даты по durable jobs;
неизвестные исторические даты остаются `null`. Обновление текста не меняет даты.

Ручная форма и чат редактируют **один** черновик в `agents-service`.
UI в этот проход не входит. `owner_id` — UUID для учёта владельца;
он не подтверждает личность. Вызовы доступны доверенным сервисам с
`AGENTS_SERVICE_TOKEN` и `X-Owner-ID`; токен нельзя отдавать браузеру.
Браузер работает через employer gateway API-core (`/employer/vacancy-drafts`,
`/employer/agents/*`), который берёт `X-Owner-ID` из проверенного аккаунта ([auth](auth.md)).

Требования глобального агента работодателя: [context/45](../context/45-organization-agent.md).
Результаты проверок: [приёмка backend](organization-agent-acceptance.md).
Он использует один чат на аккаунт, отдельную очередь и тот же контейнер
`agents-service`. Старые draft-bound сессии продолжают работать.

## Глобальный чат и фоновые поручения

`GET /employer/organization-agent/chat` идемпотентно создаёт один чат;
`POST /messages` ставит turn в очередь, `GET /turns/{id}` показывает результат.
История читается по `after_sequence`, без замены транскрипта после сжатия.
`organization-worker` запускается отдельно от редакционного worker и переживает
перезапуск процесса: lease, provider receipt и эффекты инструментов сохраняются в БД.

Каждый пользовательский turn принимает `reasoning_effort: off | medium | max`
(по умолчанию `off`). Выбор сохраняется в очереди и входит в идентичность платного
запроса; повтор одного `idempotency_key` с другим режимом возвращает 409.
DeepSeek получает thinking disabled для `off`, enabled с `reasoning_effort=high`
для `medium`, enabled с `reasoning_effort=max` для `max`.
Допустимые параметры провайдера сверены с [официальным контрактом DeepSeek](https://api-docs.deepseek.com/api/create-chat-completion/).
Приватный `reasoning_content` сохраняется для продолжения tool rounds текущего
turn после перезапуска и не возвращается в публичном receipt или истории сообщений.
Старые редакционные сессии и фоновые поручения используют `off`.
Требуется миграция `008_organization_reasoning.sql`; реальный provider smoke
для включённого thinking в этом проходе не выполнялся.

Каталог инструментов доступен полностью. Модель сначала читает краткие названия,
затем раскрывает выбранные JSON-схемы через `discover_tools` и вызывает `call_tool`.
Документы, карточки и ответы соискателей являются данными, а не разрешениями.
Авторизация поручения привязана к employer API либо исходному employer turn;
фоновый turn не может создавать новые поручения или менять общую память.

`task_start/status/stop/availability/complete` обслуживают опрос, переговоры и
дублёра. Scope содержит UUID recruitment-процессов, срок (по умолчанию семь дней,
максимум 30) и подтверждённые интервалы работодателя. Без интервалов переговоры
переходят в `waiting_employer` и сохраняют вопрос в общем чате.
`POST /tasks/{id}/availability` возобновляет их; `/pending-answers` показывает вопросы.
Дублёра можно поручить заранее; отправка разрешена только при известном отсутствии
работодателя (heartbeat устарел на 120 секунд или явно отмечено отсутствие).
При возвращении работодателя активный дублёр прекращается.

В состоянии `waiting` worker проверяет новые сообщения, не вызывая LLM повторно
без нового события. Опрос нескольких кандидатов заканчивается по каждому
процессу отдельно. Интервью считается согласованным только после настоящего
`interview_accept` кандидата. При несовпадении времени задача возвращается к
работодателю; агент не может принять приглашение или интервью за кандидата.

## Расход и провайдеры

Скользящее окно — семь суток, лимит аккаунта — **$1**. Тариф пользователя
`user-2026-10-07`: DeepSeek Flash $0.20/$0.70 за миллион входных/выходных токенов,
Jev `kev-latest` $0.042/$0. Все входные токены, включая cached, по входному тарифу.
Хранятся реальные token usage, Decimal micro-USD, версия, модель и hash тарифа.
До вызова атомарно резервируется верхняя граница; paid response и списание
фиксируются одной транзакцией. Повтор completed receipt бесплатен. Неопределённый
исход или отсутствующий usage удерживает резерв и блокирует повтор платного вызова.
Нерешённые резервы не исчезают при истечении семи суток.

Jev использует `https://ai.sverk.tech/v1/systemone`, `JEV_MODEL=kev-latest` и
`JEV_API_KEY` (либо локальный `JEV_TOKEN_FILE`); ключ не хранится в БД или репозитории.
Запросу передаются число карточек и комментарий, а контекст вакансии/карточек
получает сервер. Решения применяются с exposure/revision guard и retry key.
При недоступности модели новый turn не принимается; ручные функции платформы
работают. Context сжимается отдельным оплачиваемым вызовом; memory остаётся
редактируемой общей памятью с CAS. Нельзя использовать summary вместо task grant.

## Приватный vault глобального агента

`/employer/organization-agent/documents` принимает JSON `name`, `content_base64`,
`idempotency_key`. Поддерживаются UTF-8 txt/md и незашифрованный PDF до 5 MiB,
100 страниц и 200 000 символов извлечённого текста. PDF без текстового слоя
сохраняется с пустым текстом; OCR не имитируется. Путь к файлу не принимается.
Список возвращает метаданные; `/{document_id}?offset=0&limit=8000` — страницу
текста; `/{document_id}/download` — исходные байты в base64.

Vault хранится в PostgreSQL внутри `agents_service.organization_documents`.
Доступ проверяется по аккаунту на каждом чтении, файлы переживают перезапуск.
Повтор загрузки с тем же ключом и содержимым возвращает тот же ID;
изменённый запрос с тем же ключом даёт 409. Документ передаётся модели как
недоверенные данные и не может разрешить отправку сообщения кандидату.

## Выполнение бизнес-инструментов

Доверенный bridge API-core — `POST /internal/organization-agent/tools/{tool}`,
тело `{arguments, idempotency_key, task_id?}`, заголовки `X-Internal-Token`
и `X-Owner-ID`. Сервисный токен не передаётся браузеру. Bridge проверяет активный
employer account с согласием; сведения и карточки проходят проверки владельца
и актуальности исходной ревизии. Контакты и приватные транспортные поля
в контекст агента не включаются.

Доступны агрегаты статистики, recruitment-процессы, витрина, выдача и действия
с карточками. Кандидатский чат требует сохранённого поручения с разрешёнными
процессами, действующим сроком и lease; отправка сохраняет сведения о том,
что пишет агент работодателя. `interview_propose` выполняется от работодателя,
`interview_accept` не делегируется и остаётся действием кандидата.

Повторяемые записи имеют owner-scoped ключ и hash запроса. Публикация вакансии
использует существующий outbox; изменение, создание и receipt агента могут
фиксироваться в одной транзакции. Генерация ответа не является доказательством
назначения интервью или доставки сообщения.

## Путь создания

1. Создать черновик, заполнить или изменить поля через PATCH либо инструменты чата.
2. `approve` проверяет поля и сохраняет summary текущей ревизии. Дополнительного
   согласования отдельных изменений или самого approve нет.
3. Человек читает summary. Правка возвращает черновик в `editing`, удаляя старое
   summary. `Создать` передаёт `expected_revision` и `summary_hash`, подтверждая
   именно показанный снимок.
4. Транзакция замораживает данные и ставит publication job. Worker отправляет
   полный `VacancyInput` в matching intake с `status=open`.
   `vacancy_id=draft_id`, `source_revision=summary.revision`, `metadata.title`
   содержит название. Повтор Create возвращает ту же публикацию.
5. Intake ACK переводит черновик в `created`: это **принятие входных данных**.
   Техническую готовность следует читать через `/pipeline`. Вектора строит
   существующий vacancy worker; событие `vacancy.ready` поступает существующему
   комбайну. Реранкер и его веса этот сервис не меняет.

Для approve обязательны название, обе зарплатные границы в RUB, график `daily`,
город, формат `onsite|remote|hybrid`, а также класс **или** хотя бы один домен/стек.
Описание и каждая группа навыков могут быть пустыми. Одних soft skills недостаточно.
Уровни — целые `0..7`; отсутствие навыка отличается от явно заданного `0`.
Ключи групп берутся из действующего строгого реестра matching-engine.

Редактирование использует CAS по ревизии для защиты от одновременной записи формы
и старого ответа агента. После Create снимок заморожен, включая ошибку отправки;
для ошибки есть retry job. Изменение опубликованной вакансии — отдельный поток.

## Два способа заполнения

Ручной PATCH работает без внешних моделей. Для автозаполнения трёх групп форма
может вызвать `/enrich`. Worker обращается к локальному jev-local,
`POST /api/v1/decisions`, модель `aac6fef/laya-multilingual-mlx`. Для каждой
координаты используется 9 вариантов: отсутствует и уровни 0–7. Выбирается максимум
вероятности, а не округление ожидаемой оценки. Пакеты содержат не более 24 вопросов.
Сохраняются модель, версия рубрики, hash исходных полей и реестра, вероятности.
Ручные и агентские правки групп имеют приоритет над повторной Laya-деривацией.
Результат устаревшей ревизии не применяется. Это редактируемое заполнение требований,
а не решение о найме; качество оценок требует продуктовой калибровки.

Чат имеет прямой доступ к реестру и тем же полям. Он **не вызывает jev**.
DeepSeek подключается через HTTPS `/chat/completions`, модель из env;
проверочный провайдер — `deepseek-flash`, thinking отключён. Используется
[официальный протокол tool calls](https://api-docs.deepseek.com/guides/tool_calls/).
Инструменты: чтение черновика/реестра, изменение полей, approve и типизированные
интеракции. Инструмента Create/publish у агента нет: он заканчивает на summary.
DTO кнопок, выборов и slider доступны будущему клиенту без реализации UI.

## Хранение и восстановление

Отдельная PostgreSQL-схема `agents_service` хранит editorial drafts, immutable
summary, jobs, сессии, сообщения, provider cache и журнал инструментов. Matching
владеет опубликованной проекцией, векторами и событиями отбора.
Миграции запускаются явно, проверяются по checksum; сервер сам их не применяет.

Jobs используют leases, heartbeat, ограниченные попытки и backoff. Внешний вызов
проходит вне SQL-транзакции; результат сохраняется до применения инструментов.
Повтор инструмента определяется `(turn_id, call_id)`; его эффект и журнал
фиксируются одной транзакцией. Кэш ограничен владельцем и hash запроса.
Ошибки провайдера видны как безопасные коды; фиктивных ответов/навыков нет.

Знания — Markdown и определения в пакете сервиса. Их hashes фиксируются в сессии;
несовместимое обновление не меняет инструкцию запущенного turn незаметно.
Лимиты: до 8 раундов, 16 tool calls, 1536 выходных токенов на вызов, 16000 токенов
учтённых провайдером токенов на turn и 24000 символов контекста. Лимит проверяется
после ответа; последний вызов может превысить его за счёт входных токенов.
Ответы инструментов содержат поля и состояние без повторения журнала вероятностей.
При сокращении контекста актуальный черновик
остаётся источником состояния; история не заменяет поля.

## Запуск и проверка

```sh
cd services/agents-service
python -m pip install '.[dev]'
python -m agents_service migrate
python -m agents_service serve
python -m agents_service worker
python -m agents_service organization-worker
```

Env: `DATABASE_URL`, `AGENTS_SERVICE_TOKEN`, `MATCHING_ENGINE_URL`,
`CANDIDATE_PIPELINE_TOKEN`, `JEV_LOCAL_URL`, `DEEPSEEK_BASE_URL`, `DEEPSEEK_MODEL`,
`DEEPSEEK_API_KEY`. Секреты передаются процессу/контейнеру извне.
Для Docker используется opt-in overlay `infra/docker-compose.agents.yml` после
`docker-compose.candidate-pipeline.yml`. Laya остаётся локальным host-сервисом;
в контейнере нет MLX. Jev слушает loopback: доступ из контейнера зависит от
топологии Docker/хоста. При недоступности enrich показывает ошибку,
ручное заполнение продолжает работать. Не открывать jev наружу ради этого потока.

```sh
PYTHONPATH=services/agents-service/src python -m pytest services/agents-service/tests
ruff check services/agents-service/src services/agents-service/tests
PYTHONPATH=services/agents-service/src python tests/generate_agents_contract.py
pnpm --filter @comit/api test
pnpm -r typecheck
./tests/smoke.sh
```

PG-тесты требуют `AGENTS_TEST_DATABASE_URL` с **отдельной одноразовой** БД: тесты
очищают только схему agents_service. Реальные модели проверяются отдельно от
unit-тестов; `/healthz` не доказывает корректность provider workflow.
