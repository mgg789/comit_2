# Статистика работодателя

`GET /api/employer/statistics` — агрегаты для вкладки «Статистика» кабинета работодателя (`Statistics` в `apps/employer/src/discovery.tsx`). Требуется employer-сессия; `owner_id` вычисляется на сервере. Кандидатские ID, контакты, тексты приглашений, зарплаты офферов и обратная связь собеседований в ответ не входят.

Параметры: `from`, `to` — включительные даты `YYYY-MM-DD` в UTC, максимум 90 дней, без будущих дат. По умолчанию последние 30 дней, включая сегодня. `vacancy_id` ограничивает весь ответ одной своей вакансией; чужая и отсутствующая вакансии дают одинаковый `404`. Используется именно vacancy ID, а не draft ID.

Ответ `employer-statistics-v1` содержит:

- `inventory`: текущие количества вакансий draft/open/closed/archived, сохранённых пар кандидат–вакансия и активных процессов найма. Эти значения не ограничены выбранным историческим периодом. Open — бизнес-статус исходной вакансии, а не утверждение о готовности комбайна.
- `current` и `previous`: количество уникальных пар кандидат–вакансия, достигших каждого этапа в выбранном и предшествующем периодах одинаковой длины. Этапы: delivered, viewed, liked, disliked, invited, accepted, interviewed, offered, hired.
- `unique_candidates`: уникальные люди, по которым было хотя бы одно учитываемое событие в выбранном периоде. Один человек в двух вакансиях — один человек и две пары.
- `daily`: упорядоченные UTC-дни, включая нулевые, с количеством событий каждого типа. Повторный показ человеку или два завершённых собеседования считаются отдельными событиями; в итогах пары каждого этапа дедуплицируются.
- `top_vacancies`: до десяти своих вакансий с наибольшим числом событий периода, с ID, названием, статусом и количеством уникальных кандидатов. При одинаковой активности порядок стабилен по vacancy ID.

Готовые графики: кольцевая диаграмма статусов вакансий, столбцы этапов подбора, линии активности по дням, сравнение с предыдущим периодом и рейтинг активных вакансий. Этапы периода **не являются вложенной когортной воронкой**: приглашение могло быть принято после завершения предыдущего периода, а лайк может прийти из витрины. Поэтому API не выдаёт необоснованные проценты конверсии между соседними этапами. Нулевой этап означает отсутствие зарегистрированных событий, а не неизвестное число.

## Источники и ограничения

API выполняет один read-only SQL-снимок общей PostgreSQL: `agents_service.drafts` для инвентаря; `feed_pipeline.exposures.served_at` для фактической выдачи; `learning_pipeline.events` с impression для подтверждённого клиентом просмотра; `feed_pipeline.decisions` для лайков/дизлайков, включая витрину; `recruitment_events` для приглашения, принятия, завершённого собеседования, отправки и принятия оффера. Предложенное собеседование не считается завершённым. История этапов сохраняется после отказа/закрытия процесса и архивирования вакансии. Сохранённые пары отражают таблицу shortlist; они не означают принятые приглашения.

Повторы идемпотентных команд не создают новых событий в исходных контурах. Запрос не читает признаки обучения, приватные карточки или документы и не вызывает внешние сервисы. Источники остаются владельцами всех записей; статистика — только проекция. SQL ограничен таймаутом 5 секунд, ответ — 90 днями и десятью вакансиями. Недоступная БД/неприменённые миграции возвращают `503 statistics_unavailable`, без подстановки нулей. При дальнейшем росте объёма событий потребуется агрегированная дневная проекция; текущий контур считает их непосредственно.

Контракт опубликован в OpenAPI API-core, типы — `packages/shared/src/statistics.ts`, клиент — `getEmployerStatistics({from, to, vacancy_id})`.

Миграции `apps/api/migrations/008_statistics_reads.sql` и matching `015_statistics_reads.sql` добавляют индексы событий процесса и owner/time для выданных карточек и просмотров. PostgreSQL-проверка с 10 000 исторических карточек подтверждает выбор индекса для ограниченного диапазона выдач и неизменность итогов. Это проверка плана на синтетическом наборе, а не production benchmark.

## Проверка

```bash
STATISTICS_TEST_DATABASE_URL=<isolated-test-db> pnpm --filter @comit/api exec tsx --test tests/statistics.test.ts tests/server-registration.test.ts
pnpm typecheck
pnpm build
```

PostgreSQL-тест использует реальные исходные миграции и синтетические записи: отдельные работодатели, роль кандидата, отзыв сессии, чужая вакансия, границы UTC, предыдущий период, повторные этапы и source retries, включая доплату за принятие нового приглашения и отсутствие доплаты для старого тарифа; две вакансии для одного человека, архивирование и пустая статистика.

### Расходы

В `expenses` четыре независимые категории расходов и временной ряд за выбранный период. Источник — durable реестр, а не количество карточек на экране. Публикация начисляется один раз на draft; приглашение один раз на процесс; просрочка один раз на событие истечения дедлайна работодателя. Ответ кандидата, истечение срока ответа на оффер и отказ кандидата не штрафуются. ИИ учитывается после provider settlement, с общей дневной нормой 10 ₽ (Europe/Moscow), переводом 100 ₽/USD и накопительным округлением в копейках.

Текущие тарифы: 398 ₽ за первую публикацию вакансии; 196 ₽ за приглашение (49 ₽ при отправке и 147 ₽ при принятии); 398 ₽ за просрочку дедлайна и 398 ₽ за некачественную ОС после ручного решения поддержки. Значение `tariffs.invitation_kopeks` показывает полную стоимость приглашения, а `invitation_send_kopeks` и `invitation_accept_kopeks` — её части. `expenses.total_kopeks` и сумма категории приглашений показывают только фактически начисленное: до принятия это 49 ₽, после принятия нового приглашения — 196 ₽. Исторические строки не переоцениваются.

При фильтре вакансии включаются только начисления с её идентификатором; общие расходы ИИ без привязки к вакансии исключены. В период без событий суммы нулевые. Расходы за некачественную ОС нулевые до решения поддержки, без автоматических эвристик. Статистические дни остаются UTC; граница дневной нормы ИИ отдельно московская.

Проверка: `EXPENSE_TEST_DATABASE_URL=<isolated-db> pnpm --filter @comit/api exec tsx --test tests/expenses.test.ts`. Тест применяет реальные API/matching/agents миграции и проверяет source retries, backfill reinstall, московскую границу суток, чтение без мутаций, ограничения владельца/вакансии, ручное решение поддержки.
