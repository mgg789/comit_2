# Matching Engine («комбайн») — механика подбора

> Цикл 1, уточнение 05.10: кандидаты уже материализуются в PostgreSQL через
> реальный intake/worker; **два отдельных вектора**, strict 37D + evidence и
> semantic Harrier 640D. Все заявленные уровни трёх групп сохраняются независимо
> от подтверждения; статус обрабатывается отдельно. Числовой strict без evidence
> не является полным входом комбайна. Полные правила v3 — [[35-candidate-pipeline]],
> текущая реализация/ограничения — [[../docs/matching.md]]. Strict-filter, основной отбор и доставка событий реализованы;
> реранкер и дальнейшие механики ниже остаются следующими этапами.

> Source profile принадлежит API-core: CAS revision, отдельный evidence channel,
> server-owned profile consent и durable exact-snapshot outbox. `ACK` delivery не
> означает completion vectors/PDF/pool; API-core gateway проверяет текущий source
> watermark и consent, а matching проверяет собственную ревизию и артефакты каждого
> кандидата перед выдачей.

> Сердце 35% критерия. Требования ТЗ: выдача по категориям из теста или явно
> помеченного declared grade (не из резюме), ранжирование по силе профиля + ФСП,
> соответствие потребности **с краткой объяснимостью**, фильтрация без потери
> подборки и обоснование попадания в подборку.

## Пайплайн (комбайн вакансии)

Подготовка вакансии реализована в цикле 1: owner/зарплатные границы/daily/type,
status=open, обязательный city и class ИЛИ domens/stacks. Все группы и bio необязательны;
soft-only не допускает готовность. Strict level/7 строится в общем реестре
кандидатов с requirement_mask (отсутствие ≠ явный 0). Класс не создаёт навыки.
Harrier query из bio совместим с candidate document; пустой bio → NULL.
Новая схема координат атомарно пересобирает оба пула. Ready/outbox запускает durable основной отбор через combine-worker.
Схема ниже описывает полный целевой поток; в этом проходе реализованы этапы 1–2
и доставка событий, без реранкера, FSP/freshness и feedback learning.

```
Trigger (актуальная vacancy.ready со status=open | порог изменчивости пула)
  1. Strict pre-filter  — специализация, грейд (с допусками), формат/локация, отказ от visited/pending/attractive
  2. Candidate scoring  — score = w_r·ratingNorm + w_m·matchVec + w_f·fspBoost + w_a·freshness
  3. top-k (k ≈ 20–50)  — берём в лёгкий реранкер
  4. Rerank             — тонкая модель: контекст вакансии, разнообразие, explorable-пробы
  5. Selection          — статус Selected + объяснение попадания (снапшот факторов)
  6. Selection сохраняется; бизнес-статус вакансии задаётся отдельно
```

Веса: рейтинг подтверждённого профиля весомее векторного матча (решение из видения) — стартовые w_r=0.45, w_m=0.35, w_f=0.15, w_a=0.05; калибруются на валидационной разметке.

Уточнение текущего прохода Mike: реализуются strict-filter и основной отбор,
реранкер остаётся следующим шагом. Main-v2 использует внутри класса rank по
grade/confirmed_strength, masked strict proximity с confidence по статусу и
ограниченную semantic-поправку; `grade_status=self_reported` получает явный
коэффициент 0.6 только в rating contribution. FSP/freshness без источника не
выдумываются.
Точные стартовые формулы и коэффициенты — [[../docs/matching.md]]. Это ручная
версионированная политика до обучения S5. Город обязателен для обеих сторон;
remote игнорирует расстояние, onsite/hybrid проверяет явное согласие на переезд.

## Вектора: гибрид (решение 05.10 — Q5, Q12)

- **Интерпретируемая часть** (основа): разреженный вектор фич — все заявленные
  навыки с отдельным evidence status, специализация, грейд-сигнатура, формат
  работы и домен. Косинус по этой части = объяснимость («совпадения: Go, Kafka,
  грейд middle»); self_reported не отбрасывается.
- **Плотная часть**: эмбеддинг свободного описания, модель **`microsoft/harrier-oss-v1-270m`, 640D, нормализованные** (решение Mike, 05.10): в S3 — базовая (sentence-transformers/transformers, CPU-friendly для mgg-server; MLX-вариант из jev-local — только для экспериментов на Mac), в S5 — **контрастивный дотюн** (MultipleNegativesRankingLoss) на синтетических парах «кандидат↔вакансия» из генератора. Обязателен eval base-vs-tuned на отложенных парах (Precision@5/10, MRR): тюн входит в продукт только если выигрывает у базы — иначе честно оставляем базовую и пишем это в валидацию. В pgvector — `vector(640)`.
- Вектор кандидата строится из declared structured fields и descriptions, а
  evidence/status передаются отдельными координатами. Ссылка или narrative text
  сами не создают подтверждение; rejected координата равна нулю, missing остаётся
  неизвестным.

## Что обучаем / что не обучаем (решение 05.10)

| Компонент | Статус | Детали |
|---|---|---|
| Веса скоринга w_r/w_m/w_f/w_a | **обучаем** (S5) | линейный LTR на ~30k размеченных пар из генератора; артефакт — JSON в репо, `make train` с сидом; ablation + Precision@5/10 + MRR в доку |
| Реранкер top-k | **обучаем** (S5) | pairwise-логрегрессия на фичах и интеракциях; линейный — ради объяснимости; LightGBM/LambdaMART отклонены |
| Эмбеддинги | инференс + **дотюн** (S5) | harrier-270m: базовая в S3, контрастивный дотюн в S5 с eval-гейтом base-vs-tuned |
| IRT-калибровка заданий | **обучаем** (S5) | 2PL MLE на симулированных ответах; test-retest + point-biserial в доку ([[60-testing-engine]]) |
| Вектор вакансии | **онлайн-обучение** в рантайме | α/β-апдейты + маски-гипотезы; гиперпараметры тюним на работодателях-агентах (метрика: свайпов до сходимости) |
| PDF-разбор резюме | инференс LLM (без трейнинга) | **облачная LLM** (Sverk API или РФ-облако — YandexGPT/GigaChat, 152-ФЗ: данные в РФ-юрисдикции); pydantic-схема extraction + эвристический fallback для офлайн-контура; один интерфейс клиента, переключение конфигом |
| Объяснение выдачи текстом | инференс LLM | LLM пересказывает посчитанные факторы, никогда не решает (правило AGENTS §9) |

Свои эмбеддинги с нуля, fine-tune LLM, глубокие LTR — не делаем (нет данных/времени/объяснимости). MLOps-обвес не нужен: `make train` + детерминированные артефакты в репо.

## Тиндер-фидбек (обучение вектора вакансии)

- Лайк: `v_vac ← normalize(v_vac + α·v_cand)`; скип: `v_vac ← normalize(v_vac − β·v_cand)` (отрицательный градиент, α > β — лайк весит больше).
- **Маскированные пробы (exploration)**: в фид подмешиваем контрольных кандидатов (высокий грейд/неподходящий вектор; низкий грейд/подходящий). Коррекция применяется только к маскированной подсекции вектора (маска навыка/фичи, которую проверяем). Если реакция подтвердила гипотезу — маска снимается, изменение фиксируется; если нет — откат. Иерархия гипотез: проверяем не только сам флаг, но и коррелирующие фичи этого кандидата (каскадная проверка «а точно ли повлияло это»).
- Формулировка для жюри: «вакансия — живая модель предпочтений работодателя, дообучается на каждом свайпе; маски — это A/B-тесты гипотез о важных параметрах внутри одной вакансии».

## Правила переотбора (добор)

- Триггер: изменение пула (новые кандидаты, изменение верифицированных данных) выше порога изменчивости.
- Переотбор НЕ трогает: Visited (никогда), Pending (в процессе разбора), Attractive.
- Pending с улучшившимися данными — остаётся как есть (позиция не пересчитывается).
- Отклонённый (Rejected) возвращается в пул, если его изменение превысило **личный порог** (относительно его собственной базовой линии на момент отклонения), а не общий порог пула.

## Объяснимость (обязательна по ТЗ)

Каждый Selection несёт снапшот: `top_matched_features[]` (навык/фича + степень), `rating_points` и его состав (сколько за что подтверждено), `fsp_badges[]` если есть, `category`, `vector_match_pct`. UI показывает это карточкой «почему в подборке». Это же — обоснование попадания в кабинет работодателя.

## Валидация подбора (процедура для сдачи — 25% оценивает и её)

1. Синтетический набор: N=200+ кандидатов (синтетика по профилям специализаций/грейдов) + 10 вакансий с эталонной разметкой «релевантен/нерелевантен» (размечаем сами, протокол в документации).
2. Метрики: Precision@5 / Precision@10 (доля релевантных в топе — прямо из критериев ТЗ), MRR, объяснимость (ручная выборка «понятно ли почему»).
3. Ablation: без вектора / без рейтинга / без ФСП-буста — показать вклад компонент.
4. Тиндер-луп на синтетическом «работодателе-агенте» с фиксированными предпочтениями: вектор вакансии должен сойтись к ним за M свайпов — метрика сходимости.
