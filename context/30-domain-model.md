# Доменная модель и правила (Comit)

> Черновик v1 к обсуждению. Статусы и переходы — сердце обратной механики; здесь же обязательные правила видимости из п. 2.2 ТЗ.

## Справочники

- **Специализация** (справочник команды): backend, frontend, fullstack, mobile, data-engineer, data-science, devops, qa, ml-engineer, analyst… (MVP: 6–8 направлений).
- **Грейд** (общепринятая шкала): intern, junior, junior+, middle, middle+, senior (MVP: 4–5 ступеней).
- **Категория = специализация × грейд** (например, «бэкенд-разработчики с опытом до года»). Присваивается ТОЛЬКО через опрос + грейд-тест, не из резюме.

## Сущности

### Пользователи
- `Account` (роль: `candidate` | `employer`; один нормализованный email глобально
  уникален и роль не меняется). Вход passwordless: email OTP → HS256 JWT + hash
  revocable DB session; пароль не хранится.
- Account consent (`processing`, version, server timestamp) нужен для создания
  аккаунта. Это отдельное согласие от candidate profile/pool publication consent.
- `CandidateProfile` и `Company` остаются отдельными будущими сущностями; создание
  Account само по себе не публикует профиль и не связывает legacy UUID.
- `Company` (employer-профиль: название, описание, направление, контакты).
- `CandidateProfile` (ФИО, контакты, город, о себе; приватность-настройки; fspId nullable).
- `FspProfile` (nullable, мок-данные): разряд, рейтинг, турниры/призовые места, сертификаты, дата последнего участия. Отсутствие — нормальный сценарий (обязательная обработка по ТЗ).

### Верификация и рейтинг
- `VerifiedClaim` (тип: опыт работы | реализованный проект | навык | грейд-тест | ФСП-достижение; payload; статус: pending/verified/rejected; начисленные очки).
- `RatingLedger` (история начислений очков; итоговый `ratingPoints` — денормализовано на профиле).
- Начисление очков — за подтверждаемые факты (см. открытый вопрос про веса, Q8).

### Тестирование
- `TestBlueprint` (шаблон задачи: специализация, тема, тип, параметры, базовая сложность, дискриминативность).
- `TestSession` (кандидат, вид: grade | regular | vacancy-micro, сид варианта, ответы, скор, длительность).
- `GradeAttempt` (заявленный грейд, результат: confirmed | offered-lower | offered-higher, дата; cooldown на смену грейда — дефолт 3 месяца).

### Вакансии и подбор
- `Vacancy` (цикл 1): owner_id, status, zp_min/zp_max, daily, type, bio,
  необязательный class, словари domens/stacks/soft_skills с уровнями 0–7.
  Для готовности нужны owner_id, city (для всех форматов), обе зарплатные границы, daily, type, status=open
  и хотя бы class ИЛИ непустой domens/stacks. Soft skills одни не достаточны.
  Неполные снимки сохраняются, но не публикуются для комбайна.
- Канонические классы intake: backend/frontend/fullstack/mobile/devops/data/qa/ml;
  back/front/ML нормализуются. `ml` самостоятельный класс, не синоним data.
- `VacancyVector` (плотная часть — эмбеддинг описания; интерпретируемая часть — веса фич; версия; объяснимый снапшот).
- `Selection` (vacancyId × candidateId: score, объяснение попадания, стадия, история стадий).

### Контакт и найм
- `Invitation` (vacancyId nullable — приглашение возможно без вакансии!; offer description, salaryFrom/salaryTo обязательно, способ связи, статус).
- `InterviewSlot` / `Meeting` (время, формат, статус) — если берём пост-отбор в MVP.
- `Feedback` (сторона: employer | candidate; текст/анкета; обязательность при отказе).
- `Application` (классический отклик на вакансию — допфункционал 7%).

## Статусные модели

```
Vacancy business status: draft | open | pending | closed | done
Vacancy preparation: draft → queued → processing → ready
                              ↘ retrying → failed (manual retry)

Candidate-in-category: Registered → Tested(category assigned) → InPool

Selection (кандидат в вакансии):
  InPool → Selected (top-k после реранкера)
         → Visited (rejected в тиндре; НЕ возвращается в пул этой вакансии никогда)
         → Attractive (лайк; пул одобренных)
         → Invited (отправлено приглашение)
  Отклонённый → возврат в InPool при превышении личного порога изменения профиля

Invitation: Sent → Viewed → Accepted | Declined
  Accepted → раскрываются контакты кандидата → Meeting flow → Offer | Rejected(+Feedback обязательный)

Application (доп): Sent → Viewed → Accepted | Declined (статусы видят обе стороны)
```

Уточнение Mike от 05.10 заменяет прежние Active/HasCandidates/Suspended/Archived.
Техническая готовность отдельна от бизнес-статуса; только open допускает ready.
Изменение снимка или закрытие немедленно отзывает ready. Автоматические переходы
по SLA и стадиям найма этим intake не реализуются.

## Правила видимости (обязательные по п. 2.2 ТЗ — проверяемость на ревью)

1. ЗП «от–до» в рублях **обязательна** в вакансии И в приглашении; кандидат видит условия до начала общения.
2. Приглашение содержит: описание предложения, ЗП, название компании, способ связи. **Контакты кандидата раскрываются только после принятия приглашения или самостоятельного отклика.**
3. Статусы приглашений и откликов видят обе стороны (отправлено/просмотрено/принято/отклонено).
4. Регистрация по email с OTP-подтверждением адреса. Код не пишется в логи: он
   уходит через durable encrypted SMTP outbox; API подтверждает только постановку
   отправки. Верификация компаний и модерация вакансий в MVP не требуются.
5. Кандидат видит только свои приглашения/отклики. Работодатель не видит контакты до принятия. Попадание в подборку кандидату не показывается (наше правило) — только агрегированная статистика.

### Реализованные границы API

- Employer draft/agent endpoints получают owner из проверенного JWT/cookie; клиентский
  `X-Owner-ID` не определяет владельца. Candidate pipeline и owner PDF используют
  только собственный `account.id`.
- Public matching Selection, published vacancy profile CRUD и candidate profile CRUD
  пока отсутствуют; internal engine endpoints требуют сервисный token.

## Категория и грейд — правила из ТЗ

- Грейд не понижается принудительно: не прошёл на заявленный → тест на уровень ниже; прошёл уверенно → повышение.
- Смена грейда ограничена по времени (наш дефолт — не чаще 1 раза в 3 месяца; cooldown настраиваемый).
- История опроса и тестов доступна кандидату (кабинет: «Категория и грейд»).
- Ранжирование внутри категории: сила подтверждённого профиля (ratingPoints) + достижения ФСП сверху.

## Что НЕ входит в домен MVP (концептуально, за рамками)

- Верификация компаний-работодателей, модерация вакансий (концепция защиты от фиктивных вакансий).
- ATS-интеграция (концепция: webhooks, экспорт).
- Чаты общего назначения вне контекста приглашения (обсуждаем скоуп — Q3).
