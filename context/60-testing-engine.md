# Testing Engine — механика тестирования кандидатов

> 25% критерия + функциональное требование ТЗ: «работающая механика тестирования», устойчивая к утечке заданий и обеспечивающая сопоставимую сложность. Блэк-бокс-заглушка здесь — прямой слив четверти оценки (см. спор C в [[90-debates]]).

## Две анти-цели ТЗ и наш ответ

| Проблема ТЗ | Решение |
|---|---|
| Единый набор заданий → утечка за дни | **Параметризованные шаблоны (blueprints)**: один шаблон = семейство задач; сидированная генерация бесконечного числа вариантов с одинаковыми инвариантами сложности |
| Генерация нейросетью под каждого → несопоставимая сложность | **Сложность зашита в шаблон**, а не в генерацию: параметры варьируются в калиброванных пределах; автопроверка детерминирована; LLM не пишет задания в MVP |

## Blueprint: анатомия

```yaml
id: algo-two-sum-variants
specialization: backend
topic: алгоритмы/хеш-таблицы
type: code            # code | quiz | code-review | approach
difficulty: {base: 0.55, discriminative: 0.4}   # калибруется по статистике прохождений
params:
  input_size: {range: [10, 10000]}
  data_type: {enum: [ints, strings, pairs]}
  twist: {enum: [duplicates, negative, sorted]}
  seed: auto
check: autotests      # детерминированная проверка + лимиты времени/памяти
```

Вариант = instantiate(blueprint, seed) → у каждого кандидата свой текст/входные данные, одинаковая структура и сложность. Утечка одного варианта не компрометирует семейство.

## Типы заданий MVP

1. **Code (автотесты)**: 1–2 функции, таймаут, тесты на граничные случаи. Песочница: subprocess в контейнере без сети.
2. **Quiz**: концепции специализации (инварианты, сложность, инструменты) — быстрый скоринг.
3. **Approach («предложи подход»)**: свободный текст — в MVP рубриковая проверка (ключевые слова/структура) или лёгкая LLM-оценка с фикс. промптом; в документации честно пометить.

## Грейд-тест (первичное тестирование)

1. Опрос по отрасли и специализации (калибровка вопроса) → кандидат **сам** выбирает заявленный грейд.
2. Адаптивная сессия (CAT-lite): стартовые задачи по заявленному грейду → по результатам буст/снижение уровня внутри сессии → итог: `confirmed | offered-lower | offered-higher`.
3. Не прошёл на заявленный — может пройти на уровень ниже (по ТЗ); прошёл уверенно — предложение повысить; **понижение принудительным не бывает**.
4. Cooldown смены грейда: 1 раз / 3 месяца (настраиваемо), история попыток видна кандидату.

## Согласованный дизайн (09.10.2026) — [[../../docs/testing-design.md]]

Целевой контур зафиксирован в [docs/testing-design.md](../docs/testing-design.md);
ключевые решения, уточняющие этот документ:

- Банк MVP: **7 семейств** — домены `algorithms`/`sql`/`rest_api`, стеки
  `python`/`react`/`docker`, soft `teamwork`; уровни L1–L4; генерация вариантов
  LLM **офлайн-воркером в банк** с дневным ledger-лимитом (рантайм LLM не вызывает).
- Типы: MCQ ~50 %, код ~25–30 % (скрытые тесты в песочнице, эталонное решение
  обязательно), развёрнутый ~20–25 % как tie-breakers (рубрика → предчеки →
  DeepSeek-судья; грейд решает только агрегатор).
- Адаптивность: старт L2, бисекция сложности, SPRT-подобный ранний выход,
  потолок 30 заданий.
- Паноптикум: focus (Page Visibility) + YuNet на клиенте (onnxruntime-web);
  работодатель видит только бейдж присутствия (Хороший/Нормальный/Средний/
  Низкий/Не определён), счётчики — оператору. Кадры по умолчанию не покидают
  устройство; согласие покрывает обработку/хранение 90 дней; **контур полной
  записи (видео + экран, TTL 90 дней) полностью подготовлен и включается
  одной env-переменной**.
- Анти-слив: параметризация + перемешивание, мораторий экземпляра (3 показа /
  24 ч), дневной refill, карантин по аномалиям скорости; идентичность кода —
  нормализованная похожесть на недавние сабмиты; черновые адаптеры AI-детекции
  (OpenAI/Google) готовы и не подключены.
- Cooldown: пересдача — 7 дней, подтверждение повышения — 30 дней; сырые
  ответы и прокторинг-агрегаты — 90 дней, затем агрегаты.
- Валидация (25%): test-retest, дискриминативность (point-biserial),
  экспертная сверка N=30 (заодно калибрует судью), демонстрация утечки.

## Регулярные короткие задания (допфункционал, +7%)

- Пул микро-задач от работодателей (компания публикует mini-challenge в контексте своей вакансии/стека).
- Планировщик периодически предлагает кандидату задачу → решение/подход → результат обновляет «свежесть» профиля (freshness в скоринге) и даёт работодателю свежий сигнал.
- MVP-версия: ручной оффер задачи из пула + влияение на freshness; расписание — простым cron.

## Валидация тестирования (процедура для сдачи — прямо в критериях)

1. **Test-retest согласованность**: повторное прохождение (новые варианты тех же blueprint'ов) тем же «кандидатом» → корреляция скор/грейд (цель: стабильный грейд, покоящийся в той же ступени).
2. **Дискриминативность**: синтетические «слабые/сильные» сессии (генерим заведомо ошибочные решения) → разделяет ли скор классы (цель: заметный разрыв, точечная метрика — point-biserial).
3. **Соответствие экспертной разметке**: команда вручную оценивает N=30 решений → совпадение с автоматическим скором.
4. **Устойчивость к утечке**: демонстрация — «слитый» вариант не даёт преимущества (следующий вариант того же шаблона не решается по шпаргалке).

## Реализация

- `testing-engine` (Python/FastAPI): реестр blueprint'ов (YAML в репо + БД), генератор вариантов, раннер песочницы, скоринг.
- UI в приложении кандидата (сессия теста) + отдельный фронт `apps/testing` для расширенного сервиса (микро-задачи, техсобесы — по остаточному принципу, Q3/Q12).
- Минимальный банк для MVP: 3 специализации × ~6 blueprint'ов × 2 уровня = ~36 шаблонов. Этого достаточно для демо и валидации.


## Реализованный браузерный контур — 11.10.2026

Уточняет описание реализации выше, не меняет целевые критерии ТЗ. Кандидат
подтверждает конкретное семейство навыков; общий заявленный профессиональный
грейд не заменяется результатом теста одного навыка. Подготовка не расходует
попытку, Start сохраняет согласия. Доступны MCQ и короткие ответы с серверной
детерминированной проверкой. Код и развёрнутые ответы не выдаются в браузерной
сессии: существующий code-judge пока не исполняет задания, имитировать проверку
нельзя. Целевые квоты этих типов пока не достигнуты.

Присутствие лица определяется локальным MediaPipe BlazeFace вместо ранее
планируемого YuNet. Полный экран и потеря фокуса учитываются в окне 30 секунд.
Запись разрешается отдельными согласиями на 90 дней и только при серверном
`TESTING_RECORDING_MODE=full`; по умолчанию остаются агрегаты. При отказе от
камеры работодатель видит отказ отдельно от технической недоступности.
Перезагрузка возобновляет ту же попытку, ответы и фрагменты записи идемпотентны.
Пересдача через 7 дней, повышение через 30 дней — актуальное правило вместо
раннего трёхмесячного интервала.

## Статус недельной практики (2026-10-11)

Реализованы еженедельные задания самой платформы: три коротких вопроса, одна отправка на аккаунт/UTC-неделю, 2/3 для отметки активности до следующего понедельника. Грейд не меняется; matching учитывает отметку только среди близких по main score кандидатов. Пул задач работодателей из раздела выше остаётся отдельным будущим расширением. [Контракт](../docs/weekly-challenges.md).


### Статус реализации защиты и валидации — 11 октября 2026

Прежний relaxed-fallback удалён: уже показанный экземпляр не выдаётся
повторно. Офлайн-генерация действительно изменяет параметры и вычисляет ответ
в семи YAML-семействах; обязательный код получает новые скрытые входы при
сохранении базовых edge cases. MCQ перемешиваются с приватным переназначением
ответа и сохранением порядка в сессии. Совпадение токенов кодовых решений
журналируется для ручного разбора, но не отменяет независимый правильный вердикт.
Валидация содержит 84 разноуровневых синтетических профиля и семь семейств;
фактические метрики и ограничения — `data/validation/testing-validation.json`.
Экспертная калибровка сложности и человеческая test-retest выборка этим не
подменяются и не объявлены выполненными.
