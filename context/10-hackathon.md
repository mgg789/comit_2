# Контекст хакатона: ЛЦТ 2026, спецтрек ФСП

## Что это

**ЛЦТ 2026** — восьмой хакатон «Лидеры цифровой трансформации» (Москва). Наш трек — **специальный трек от Федерации спортивного программирования (ФСП)**: платформа-агрегатор ИТ-вакансий с верифицированным профилем достижений участника ФСП. Приз до 1 000 000 ₽. В рамках спецтрека участникам также доступно получение разряда по спортивному программированию.

## Смысловой центр конкурса (что хочет ФСП)

1. **Обратная механика (LHH-модель)** — инициатива у работодателя: он просматривает категоризированную базу и сам направляет приглашение конкретному человеку с предложением и ЗП. НЕ классический отклик кандидата на вакансию. Это 35% оценки.
2. **Категория = специализация + грейд**, присвоенная обязательным путём (опрос → самостоятельный выбор грейда → тест на заявленный грейд), а не самоописанным резюме.
3. **Механика тестирования, устойчивая к утечке заданий** и обеспечивающая сопоставимую сложность — 25% оценки.
4. **Обогащение профиля достижениями ФСП** — творческая задача: сами придумываем структуру данных и показ; API не дадут; обязательна корректная обработка отсутствия ФСП-истории. Удачные решения ФСП возьмёт в реальную интеграцию — это шанс повлиять на настоящий продукт.
5. **Своя процедура валидации** решения + результаты (оценивается и решение, и качество валидации).

## Что ФСП прямо хочет увидеть (чтение между строк ТЗ)

- Обратную механику как **ядро**, а не фичу: кандидат не «шлёт резюме в никуда», работодатель получает осмысленную, объяснимую подборку.
- ML/NLP в подборе и разборе резюме = явное преимущество при оценке (п. 3.2 ТЗ).
- Готовность к интеграции: Keycloak-совместимость (ориентир), схема интеграции с реестром ФСП в документации.
- Добросовестный продукт: 152-ФЗ, приватность, ЗП обязательна, контакты скрыты до принятия — правила видимости жёстко зафиксированы в п. 2.2 ТЗ.
- Для «за рамками MVP» (фиктивные вакансии, ATS) — ожидается **концепция и архитектурный подход**, не код. Это дёшево и даёт баллы: оформить документом.

## Сдача

- **Промежуточная**: репозиторий + краткое описание механики подбора и тестирования с обоснованием + демо промежуточной версии с базовым сценарием.
- **Финальная**: репозиторий (обязательно) + презентация pptx/pdf (обязательно) + развёрнутый прототип (крайне желательно; у нас есть свой сервер — развернём) + документация doc/pdf (обязательно).
- В демо нужен сквозной сценарий: регистрация соискателя → опрос → тест → категория → поиск работодателем → приглашение. Отдельно показать и объяснить механику тестирования и механику подбора.
- Документация (обязательно): архитектура, механика тестирования + обоснование устойчивости, механика подбора и категоризации, процедура валидации + результаты, схема интеграции с ФСП, описание API (OpenAPI), библиотеки с версиями, инструкция сборки/запуска.

## Выводы для планирования

- Окно разработки — **около недели** (5–11 октября). Вся архитектура и скоуп должны быть согласованы под демо 11 октября + документацию.
- 60% оценки — механика подбора (35%) + тестирование/валидация (25%). UI и техпроработка — 17%. Значит: сначала движки и их объяснимость, потом полировка.
- Допфункционал (7%) — это всё «необязательное для MVP» из ТЗ: отклик на вакансии, публикация вакансий, регулярные задания, концепция защиты от фиктивных вакансий/ATS, адаптив. Часть у нас и так в видении — расставить приоритеты по дешевизне.
