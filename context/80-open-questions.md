# Открытые вопросы и развилки (нужны решения Mike)

> Формат: контекст → варианты → рекомендация. Решения фиксируем здесь же после обсуждения (таблица решений внизу).

## Продуктовые развилки

### Q1. Команда и роли
Кто в команде, сколько человек, кто за фронт/бэк/ML/презентацию? От этого зависит всё планирование (4 фронт-приложения и 2 Python-сервиса одному не унести).
**Варианты:** соло с агентами / 2–3 человека / 4+.

### Q2. Дедлайны промежуточной сдачи
По VK спецтрека: разработка 5–11 октября, итоги 30 октября. Дата промежуточной сдачи (репо + описание + демо) не известна — вероятно 8–11.10.
**Действие:** уточнить у организаторов в первые сутки; к 8–9 октября иметь сквозной сценарий в любом состоянии.

### Q3. Глубина пост-отбора (собесы/чат) в MVP
Видение: карточка работодателя у кандидата, чат, выбор времени собеса в интерфейсе, тестовые, оффер/отказ с формой, SLA-штраф. Это много UI и стейтов за 1 день плана (сб 10.10).
**Варианты:** (a) полный flow с чатом и слотами; (b) без чата: принятие приглашения → выбор слота из предложенных → статус встречи → оффер/отказ + обязательная форма обратной связи + SLA-штраф; (c) только статусы приглашения + оффер/отказ + форма (без встреч).
**Рекомендация:** (b) — сохраняет решение проблемы «молчания» (SLA + обратная связь) и демонстрируемый жизненный цикл, но без самого дорогого (чат-инфраструктура). Чат — концепция в документации.

### Q4. Фронтенд: 4 отдельных приложения vs один shell
Видение — 4 независимых web app. Риск: 4 сборки/деплоя, дублирование auth/UI, потеря времени при жёстких сроках.
**Варианты:** (a) 4 отдельных приложения как задумано; (b) одно приложение с ролевым роутингом; (c) монорепо `apps/*` с общими packages (ui-kit, api-client, types) и независимыми сборками.
**Рекомендация:** (c) — внешне остаются отдельными приложениями (как в видении), но дубли исчезают. При команде < 2 фронтендеров рассмотреть (b) для welcome+витрина, объединив с candidate.

### Q5. Вектора: плотные vs интерпретируемые vs гибрид
Видение — «аналог эмбеддингов слов» (плотные). Проблема: чёрный ящик для объяснимости (обязательна по ТЗ) + холодный старт + время.
**Варианты:** (a) плотные эмбеддинги везде; (b) разреженные интерпретируемые фичи; (c) гибрид: интерпретируемые — основа скоринга и объяснений, плотные — один из сигналов.
**Рекомендация:** (c). Объяснимость «почему в подборке» строится из фич, а эмбеддинг добавляет качество на синонимии. Дешевле в реализации и надёжнее в демо.

### Q6. Контрольные пробы (маски) в MVP
Подсовывание калибровочных кандидатов с маскированной коррекцией вектора — оригинально, но добавляет сложности в фид и рискует запутать демо.
**Варианты:** (a) в MVP с визуальным выделением для жюри; (b) механика в коде, но не выделена в UI; (c) только концепция.
**Рекомендация:** (b) — реализовать простую версию (1 маска на N свайпов), в демо показать слайдом/в dev-панели, не смешивать с основным тиндер-потоком.

### Q7. Keycloak в MVP
ТЗ: Keycloak-совместимость — ориентир, не требование. Ставить Keycloak в compose — +~1 ГБ памяти и время настройки.
**Варианты:** (a) Keycloak в compose сразу; (b) свой email+JWT, но с claims-структурой Keycloak и OIDC-швом в документации; (c) Zitadel (уже есть опыт).
**Рекомендация:** (b) — дешевле, а совместимость демонстрируем документом и структурой токенов.

### Q8. Верификация полей и веса рейтинга
Рейтинг — очки за подтверждённое. Но кто подтверждает «опыт работы» в MVP без реальных проверок?
**Варианты:** (a) все поля самоподтверждаются, очки за структурированность+тесты; (b) мок-верификация (статус pending → verified по времени/флагом модератора для демо); (c) очки только за объективное: тесты, ФСП, выполненные проекты (ссылки/репо).
**Решение:** source profile хранит декларации и evidence раздельно. Self reported
grade допускается в пул с явным badge; `main-v2` применяет confidence 0.6 только к
его rating contribution. Skill/narrative самооценка не создаёт подтверждённые
очки; ссылки и текст не превращаются в evidence автоматически.

### Q9. Какие данные ФСП-профиля моделируем
API не дадут — придумываем сами. Отображение работодателю — творческая задача.
**Предложение-старт:** разряд (III→I, КМС, МС), рейтинг-число (ELO-подобный), турниры (название, год, место), сертификаты школ/курсов ФСП, активность (последнее участие). UI: бейджи + блок «Спортивный профиль» в карточке кандидата + фильтр «есть подтверждённые достижения ФСП». Влияние: fspBoost в скоринге + приоритет в ранжировании внутри категории (прямо из ТЗ).

### Q10. SLA-штраф вакансии (4 дня блокировки) — в MVP?
Наша фича против «молчания». Риск для демо: заблокированная вакансия ломает сценарий.
**Варианты:** (a) в MVP как задумано; (b) в MVP, но мягче (warn → ограничение только новых приглашений, подборка работает); (c) концепция + warn-статус.
**Рекомендация:** (b): демо-безопасно, механика видна, на слайде объясняем полную версию.

## Технические развилки

### Q11. NestJS vs Fastify для api-core
NestJS — структура и Decorator-based OpenAPI, но тяжелее и «магичнее»; Fastify — быстрее и проще, schema-based swagger.
**Решение:** Fastify + TypeScript NodeNext ESM с schema-based OpenAPI. Это фактический
стек `apps/api`; NestJS/Prisma в проекте не используются.

### Q12. Эмбеддинг-модель для плотной части
Локальная ru-friendly модель без GPU: предложения — bge-m3 / multilingual-e5-small / laiy (локально уже есть Harrier/Laya в jev-local). API внешних сервисов (OpenAI и пр.) — против правил (память не отправлять наружу; и вообще демо должно жить офлайн).
**Рекомендация:** multilingual-e5-small или bge-m3 через sentence-transformers в matching-engine; размер ~0.1–2 ГБ — приемлемо.

### Q13. Раннер кода в тестах
Песочница: subprocess + ресурсные лимиты в отдельном контейнере; чужие тяжёлые решения (judge0, isolate) не тащим.
**Рекомендация:** свой мини-раннер (python docker exec с таймаутом/памятью) — 0.5 дня работы, достаточно для MVP.

### Q14. Где разворачиваем прототип
ТЗ: крайне желательна ссылка на развёрнутое решение. У нас есть свой сервер (mgg-server) и опыт публичного стенда Navix.
**План:** docker-compose на сервере + seed-данные + демо-аккаунты. Фактический
production/server deploy этим документом не подтверждается.
